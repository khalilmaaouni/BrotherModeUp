Act one

The pain

Six short sections. What is going wrong, what stops it immediately, what stops it coming back, and the one incident that started all of this.

You should not have to become the project manager for your AI

The more work you hand to Claude, the more invisible coordination work comes back to you.

You already wear every hat. Founder, product manager, builder, reviewer, analyst, release owner. Claude gives you far more execution capacity than you had last year, and that is the good news.

Here is the part nobody warns you about. More AI creates more coordination.

What you end up doingHow often it shows up
Repeating context you already gaveEvery new session
Remembering decisions nobody wrote downEvery time one comes back
Tracking which agent is touching which fileEvery time you run two
Reconstructing where an interrupted session stoppedEvery crash, every compaction
Working out what actually changedEvery review
Re-running the checks yourselfEvery time you do not trust done
Deciding whether done is realEvery single time

Eventually you are the memory, the traffic control and the quality gate for your own AI.

The painkiller: take the coordination out of your head

Four things stop hurting on day one.

One person. More leverage. Less babysitting.

Memory and recovery, the ownership refusal and the evidence discipline are each marked certified in the capability register, with a named test behind them. The project page is beta. Act five prints the whole register with the gap beside each entry.

The medicine: stop the same failures becoming your normal way of working

Fixing today's interrupted session is worth something. It is not the interesting part.

The interesting part is that four failures keep coming back, and each one is closed by a different step in the same loop.

The painkiller makes today's project easier to control. The medicine is meant to make the way you work harder to fool, forget or silently break.

The honest size of the medicine claim

Six of the seven steps above are enforced by machinery. The last one, LEARN, is thinner than the rest, and you should know exactly how thin before you buy the idea.

The correction-learning system is real code you can run. It captures a correction, promotes it to a rule behind a human-confirmed receipt, retrieves it later with its reason shown, and grades whether it prevented rework. But it carries no state in the capability register, it has no slash command and is not on the everyday surface, and its own page states that not one hour of real founder work has yet gone through it. The weekly review that closes the loop is twenty minutes of a human's time, nagged at session start, and nothing performs it for you.

So: the medicine is a discipline this system asks of you and reminds you about. It is not learning that has been shown to work, and it is not automatic. If nobody ever runs the weekly review, you are paying the overhead and collecting only the painkiller.

The command line is tools/bm_learn.py and its page is docs/CORRECTION-LEARNING.md, including the sentence about zero founder hours. Searching capabilities.status.json for a learning entry returns nothing, and grep -rl bm_learn skills/ commands/ returns zero files.

The silent overwrite

You have Claude refactoring your pricing logic in one window.

Twenty minutes later you open a second session to add a field to the same feature, because that is how the day actually goes.

You have forgotten the first session is still holding one shared file.

Both finish. Both report success. One of them silently erased ninety minutes of the other's work.

Nothing crashed. Nothing warned you.

That is the incident this system was built around. It happened with two people driving, and it reaches one person the moment you run two windows, which is most days.

A rule in a prompt is not a control. A control is a check that runs.

Remembers, protects, proves

Three things a real project needs that a conversation cannot guarantee.

PillarWhat it meansThe limit to hold it to
REMEMBERS Goal, decisions, tasks, ownership, evidence and next intent live in a durable record, so the project survives the chat. Right before context is compacted, your whole working tree including untracked files is snapshotted to a private local git reference. A snapshot is a rescue, not a backup service: it lives in your own .git and goes when that goes. Recovered work is owner-only on POSIX, not on Windows.
PROTECTS Two workers cannot write one file. The second is refused by a program before its write executes, rather than asked nicely afterwards. Not an operating-system sandbox. Supported editing tools are refused; a plain shell write is detected afterwards, not prevented. Verified on Claude Code only: measured on one other runtime, the refusal did not fire at all.
PROVES Done is a gate result, not agent confidence. A verifying command must run after the last edit, pass, and be quoted back. The gate proves the checks that ran. It cannot tell you the acceptance criteria you chose were the right ones for your business.

Register states and the test behind each are in capabilities.status.json. The runtime measurement is docs/mistakes/M19-the-codex-fence-does-not-fire-in-exec-mode.md. The fifteen points behind done are references/definition-of-done.md.

What it is, and three things it is not

BrotherMode is the reliability layer for Claude Code: it keeps your project memory, your AI workers and your proof together across sessions.

It is notBecause
another AI modelClaude remains the intelligence. This adds no reasoning and never claims to.
a collection of promptsThe controls that matter sit outside the model's own judgment, as programs with exit codes.
an agent marketplaceThe goal is not the maximum number of agents. It is the smallest correct amount of delegation.

Most tools help Claude do more. BrotherMode helps you trust more of what Claude does.

Act two

One builder, one product, one week

You, alone, shipping offline mode for your app: cache the last screen, sync on reconnect, show the user which state they are in. Five days. Every command appears where the week needs it.

Monday

Start with the outcome, not a thirty-page spec

/brothermode:start Offline mode: cache the last screen, sync on reconnect,
and show the user which state they are in.

One sentence. What comes back is not a plan; it is a short conversation that asks only the questions whose answers change the scope, then writes the brief and puts one decision in front of you.

Tuesday

/brothermode:status

Eight fields, every one computed from the project's own records rather than from the conversation. Real output, pasted exactly as printed from a run against a throwaway repository on 8 August 2026:

  work budget: input ?, output ?, total 600k to 1.1M

  The offline banner clips its second line on a small phone

  why: the outcome is recorded, and nothing can run until you authorise it

Look at what it refuses to do. It does not invent a direction. It never gives a bare date, because a bare date is a false promise, so the forecast is a range with a confidence. It does not claim evidence it does not have. And the next step it recommends is not a task at all: it is asking you for authority, because nothing runs until you give it.

Then there is the page you open when you want the project rather than the conversation:

/brothermode:view

That writes one self-contained file at the top of your project folder. No sign-in, no network, opens by double-clicking. Its real section headings, read out of a generated page:

Where this stands            What could still go wrong
Waiting on you               Decisions waiting for your answer
Your next step               What I now believe, and what proved it
The path of the work         What has to be true before this ships
How far each lane has moved  Who holds the pen
How much, against what limit The story so far
                             Your move

The eight fields and their order are fixed by references/status-view.md, and the ban on a bare date is references/forecasting.md. Publishing that page as a shared link is beta and needs a paid plan plus four further conditions; the file on disk is the promise.

A dead session should cost minutes, not the project

Your laptop sleeps mid-task, or the context fills, or you kill the window by accident.

Thursday

The best time to find out you are wrong is before your users do

/brothermode:review

Everything looks finished. This is the one command in the product whose job is to disappoint you.

Friday

Deliver something you can stand behind

/brothermode:deliver

The packet is generated from the records rather than filled in by hand, so what it claims and what the store holds cannot differ. It answers what was built, what was checked and when the checks ran, what failed and was fixed, what was excluded on purpose, and what uncertainty remains. And it refuses the words ready to deliver unless every acceptance check has evidence produced after the final edit.

Two limits on the packet, both worth knowing before you rely on it

It proves the verification that was recorded. It cannot tell you the acceptance criteria you picked were the right ones for your business. That judgement stays yours.

And you have to ask for it. In the project's own internal comparison, the deliver-packet task failed in both arms: neither configuration reliably produced the packet without being asked. Run the command; do not assume proof appears on its own.

Act three

Your judgment

What stays yours, what it can take off you, and the honest test for whether it is worth the overhead at all.

You are already the team

Five hats, and you swap between them all day. Each gets what the tool actually does for it, and the part of it you will resent in week one.

HatThe question you are askingWhat it does for youWhat you will resent
FounderWhat are we actually trying to achieve? Outcome framing, scope in and out, decisions recorded with the condition that would flip them, and the standing option to take any decision back. It asks before it moves. On a day you just want momentum, that reads as friction.
BuilderWhat should Claude work on next? One recommended next step with its reason, scoped work, file ownership, continuity across sessions. Claiming files before writing them feels like paperwork, right up until the first refused collision.
ReviewerDoes this actually work? Fresh checks after the final edit, independent review on substantial work, uncertainty stated rather than implied. It is designed to disappoint you on Thursday. That is the feature, and it still stings.
AnalystCan I trust this number? A second independent derivation before a figure is shown, and the word unverified next to any number that could not get one. Describing a table and sampling rows before querying feels like ceremony, until it catches a column whose name lied.
OwnerCan I ship this, or hand it over? A delivery packet, a project page anyone can open, and handover material generated from the records. How often a field says not forecast yet. That is information, but it takes a week to stop reading it as a gap.

It does not remove these responsibilities. It reduces the coordination cost between them.

When it earns its overhead

Four questions, in order

  1. Will more than one session or worker ever touch these files? Yes: you want the refusal.
  2. Will this work outlive one session? Yes: you want the record.
  3. Does being wrong cost money, credibility, or a rollback? Yes: you want the gate.
  4. Will you actually run the weekly review? No: use something lighter, and take only the painkiller.

Use something lighter when

  • It is a one-shot question with a self-contained answer.
  • It is a throwaway script nobody will run twice.
  • You are brainstorming, and ceremony would kill the momentum.
  • The task is small enough that verifying it is obvious.

Serious work deserves more structure. Small work does not.

How it works, and why trust it

Now the machinery, once you have a reason to care about it.

The architecture, by responsibility

The controls, the skills and the workers

Three controls that are programs rather than requests

ControlWhat it doesIts stated limit
The write refusalRuns before a tool call executes and blocks a write to a file another live claim covers.Fails open by design and says why, so a refusal always means a real conflict rather than a broken hook. Does not gate arbitrary shell writes.
The snapshotCaptures the whole working tree, untracked files included, right before context is compacted.A local git reference, never pushed. A rescue, not a backup service.
The cost recordWrites what a session actually spent in tokens, tool calls and time, from a hook rather than from the model.Nothing is recorded until you consent, and a test refuses any write before consent exists.

A model reporting on its own performance is not evidence. That is the reason the third one is written by a hook rather than by Claude.

Memory: remembering, forgetting, and the part that is only a habit

There are two memories, and confusing them is the fastest way to be disappointed by this.

The project record is per project and machine-written: objectives, decisions, tasks, claims, evidence. That is what status and delivery read from, and it is the certified half.

The vault is different. It is a plain folder of markdown you own, outside any repository, holding what should outlive the project itself. Overviews, open items, session logs, and the failures you would otherwise rediscover.

Obsidian, and why it is optional

The vault is already an Obsidian vault. Open the folder and the links become clickable, backlinks show what references the note you are reading, and the graph draws how projects, failures and decisions connect. It is free, and there is nothing to configure.

It is also not a dependency, and the project is blunt about that. Nothing in the hooks, the command line or the fence checks whether Obsidian is installed, running, or has ever been opened. The bracket links stay perfectly readable as plain text in any editor. Obsidian is a nicer window onto the same folder.

Improving, and the honest size of it

Corrections you make can be captured, promoted into a rule behind a human-confirmed receipt, retrieved later with the reason shown, and graded on whether they prevented rework. Nothing in the system, automatic capture included, can approve or promote its own candidate.

What that machinery has not yet earned

It carries no state in the capability register and no command on the everyday surface, and its own page records that not one hour of real founder work has gone through it. The weekly review that closes the loop is twenty minutes of a person's time, nagged at session start, and nothing performs it for you.

Treat improving as the part of this you have to want. The remembering and the forgetting happen whether or not you engage; the learning does not.

Documentation, and handing the project to someone else

Documentation here is generated from what was recorded, not written by hand and then left to rot. One command writes a numbered folder into your project, and it scales its own depth to the project rather than asking you to choose.

The handover pack, page by page

One command writes a folder somebody who was in none of your conversations can read straight through.

PageWhat it answers
SituationWhere it stands, what was authorised, what has been spent against the ceilings, how much is accepted, the current forecast, and anything only a person can clear.
DecisionsEvery decision, newest first, each with what else was weighed and what would have changed it.
RisksWhat is still open, each with what would settle it.
CalibrationsThe checks deliberately broken to prove a guard actually bites, with what was broken and what was observed.
LearningsWhat a reader would otherwise have to rediscover.
TimelineEvery catch-up in order, oldest first, so the run can be replayed forwards.
HandbacksEvery decision you took back, each with the page a developer picks the work up from.

The fourth one is the unusual entry. A calibration is a check somebody deliberately broke to prove the guard would catch it, because a test that has never failed is not evidence that it can.

The limit on all of this

Handover packs are beta and nobody outside the project has ever read one. If you are the first, every question the pack cannot answer is a defect in the pack rather than a gap in you, and saying so is the most useful thing you can send back.

What is proven, and how strongly

Every capability carries one of four states, read out of a register file, with a test that fails the documentation when a page and the register disagree.

StateMeansWhat sits there
certifiedProven in the tree by named evidence.One writer per file. The durable store and its recovery. Pages held to facts read out of the tree. The guided flow. Continuous integration on macOS and Linux. Consent-gated cost recording. The two-command install.
betaReal, with a named gap beside it.Windows. The controller and the autonomy contract. The decision record and catch-up. Handback and handover packs. The published project page. The hook cost measurement.

Separately from whether a thing is offered, there is how far its claim has been checked. Six rungs, and one of them is empty.

One measured result, bounded exactly as its own page bounds it

The project runs an internal comparison of two configurations of the same model, with and without BrotherMode. One task puts a rival session's claim on a file and asks the run to work on it anyway. The result:

| H1 fence-collision | 0/2 | 2/2 PASS |

Without, zero of two. With, two of two. That is the mechanism doing the one thing a prompt cannot.

Now the bounds, in the source page's own words: "Every number this benchmark produces is INTERNAL EVIDENCE: self-graded, on one machine, with no outside user. It compares two configurations of the same model against each other and nothing else. It is not a market claim, it does not rank BrotherMode against anyone else's product." Blind grading has not run. Take it as evidence the control works, not as a score against anything.

What we know, and what we still need to prove

Proven inside the treeStill to prove outside it
The write refusal, the durable store and its recovery, consent-gated cost recording, pages held to facts read out of the tree, the guided flow, and continuous integration on two operating systems. Each has a named test that goes red when the claim stops being true. That it reduces rework on a real project. Nobody has counted one. There is no recorded rework rate and no comparison against working without it.
The mechanism result above, on one machine, self-graded. A comparison somebody else can reproduce, run under the same conditions across tools.
The two-command install, exercised end to end on every release inside a throwaway configuration. An install on a machine this project does not own, reported by the person who ran it.
The full lifecycle on macOS and Linux. The full lifecycle on native Windows. Today only part of the suite runs there.

The right column is not an apology. It is the reason the left column is worth reading: a project that will not print its empty rung is a project you cannot calibrate.

Your first project

Try it on work you actually care about.

Pick something with more than one session in it, several files, a real definition of done, and at least one decision only you can make. A throwaway script will teach you nothing about this.

# once, in a terminal
claude plugin marketplace add khalilmaaouni/BrotherModeUp@v3.0.0
claude plugin install brothermode@brothermode-marketplace

# prove it is wired, including the refusal, on your machine
python3 scripts/doctor.py

Then, in your project:

WhenRun
Today/brothermode:start with your outcome in one sentence
ThenWork normally. Let it claim files before it writes them.
Tomorrow morning/brothermode:status, before you re-explain anything
Before you say done/brothermode:review
When the evidence is green/brothermode:deliver

Requirements are small: Claude Code, Python 3.9 or newer using the standard library only, and git. No account, no server, no subscription, and no API key of its own. The tools make no network calls, and you can prove that yourself in under a minute rather than believing it.

Give Claude more work. Keep control of the project.

How this was built. Every claim was read out of the BrotherMode repository at v3.0.0 on 8 August 2026: the register of capability states, the roadmap's proof rungs, the reference files behind status, forecasting, delegation and the definition of done, the frontmatter of all seventeen skills, and the two limits registers. The status block and the project-page headings in act two are real output, captured by running a project through the command line against a throwaway repository and pasted exactly as printed.

The builder in act two is an illustration. The machinery is not. Every command shown is real, every rule that bites is real, and every limit named traces to a file. The diagrams were drawn for this booklet; the tool draws five shapes of its own, and a timeline is not among them.

What this booklet does not claim. No productivity number, because none has been measured. No test count, because counts move and a reader seeing a mismatch cannot tell a stale page from a broken install. No ranking against another product, because the run that would earn one has not happened.

覚えている、守る、証明する

本物のプロジェクトに必要で、会話では保証できないものが三つあります。

柱意味併せて見るべき限界
覚えている目標、決定、タスク、所有権、証拠、次の意図が永続的な記録に残るため、プロジェクトが会話より長く生き延びます。コンテキストが圧縮される直前に、追跡外のファイルも含めた作業ツリー全体が、ローカルのgit参照へスナップショットされます。スナップショットは救助であってバックアップサービスではありません。あなたの .git の中にあり、それが消えれば一緒に消えます。復旧した作業の所有者限定権限はPOSIXのみで、Windowsでは効きません。
守る二つのワーカーが同じファイルに書くことはできません。二人目は、書き込みが実行される前にプログラムによって拒否されます。後から丁寧にお願いされるのではありません。OSレベルのサンドボックスではありません。対応している編集ツールは拒否できますが、素のシェル書き込みは事後に検知されるだけで、防止はされません。検証済みなのはClaude Codeのみで、別のランタイムで計測したところ拒否は一度も発火しませんでした。
証明する完了とはゲートの結果であって、エージェントの自信ではありません。検証コマンドが最後の編集の後に走り、通り、引用されなければなりません。ゲートが証明するのは走ったチェックです。選んだ受け入れ基準があなたの事業にとって正しかったかどうかは教えてくれません。

何であり、そうではない三つのこと

BrotherModeはClaude Codeのための信頼性レイヤーです。プロジェクトの記憶、AIワーカー、そして証拠を、セッションをまたいで一つにまとめておきます。

これではない理由
別のAIモデル知能はClaudeのままです。推論は一切足しませんし、足すと主張したこともありません。
プロンプト集重要な制御はモデル自身の判断の外側に、終了コードを持つプログラムとして置かれています。
エージェントの品揃え目的はエージェントの最大数ではありません。正しい範囲で最小限の委任です。

多くのツールはClaudeにもっと多くをやらせます。BrotherModeは、Claudeがやったことをもっと信頼できるようにします。

記憶、忘却、そして習慣にすぎない部分

記憶は二つあり、これを混同するのが失望への最短経路です。

プロジェクト記録はプロジェクトごとで、機械が書きます。目標、決定、タスク、宣言、証拠。状態表示と引き渡しが読むのはこれで、certified の側です。

ヴォールトは別物です。あなたが所有する、リポジトリの外にあるマークダウンのただのフォルダで、プロジェクトそのものより長く残すべきものを入れます。概要、未処理項目、セッションログ、そして再発見するはめになる失敗の記録です。

Obsidian、そしてそれが任意である理由

ヴォールトはすでにObsidianのヴォールトです。フォルダを開けばリンクはクリックでき、バックリンクが参照元を見せ、グラフがプロジェクトと失敗と決定のつながりを描きます。無料で、設定は不要です。

そして依存ではありません。プロジェクト自身がそう明記しています。フック、コマンドライン、拒否の仕組みのいずれも、Obsidianが入っているか、動いているか、一度でも開かれたかを見ていません。角括弧のリンクはどのエディタでもそのまま読めます。Obsidianは同じフォルダに対する、より心地よい窓にすぎません。

改善、そしてその正直な大きさ

あなたが出した修正は、捕捉し、人間が確認したレシートを経てルールに昇格させ、後から理由付きで取り出し、手戻りを防いだかどうか採点できます。自動捕捉を含め、この仕組みのどの部分も自分の候補を自分で承認したり昇格させたりはできません。

改善の仕組みが、まだ得ていないもの

能力レジスタに状態がなく、日常のコマンドもなく、そのページ自身が実際の創業者の作業を一時間も通していないと記録しています。ループを閉じる週次レビューは人間の二十分で、代わりに実行してくれるものはありません。

改善は、あなたが望まなければ起きない部分だと考えてください。覚えることと忘れることは関与しなくても起きますが、学習は起きません。

文書と、誰かへの引き継ぎ

ここでの文書は、手書きして放置され腐るものではなく、記録されたものから生成されます。一つのコマンドが番号付きのフォルダをプロジェクトに書き、深さはあなたに選ばせず自分で測ります。

引き継ぎ資料、一ページずつ

一つのコマンドが、あなたの会話に一度も参加していない人が通しで読めるフォルダを書きます。

ページ答えること
状況どこまで来たか、何が承認されたか、上限に対していくら使ったか、どれだけ受理されたか、現在の予測、そして人にしか片付けられない未処理。
決定すべての決定を新しい順に、他に何を検討したか、何があれば変わったかと共に。
リスクまだ開いているもの。それぞれ、何があれば決着するかと共に。
較正ガードが本当に効くと示すために意図的に壊したチェック。何を壊し、何が観測されたか。
学び読む人が自力で再発見するはめになること。
時系列すべての進捗報告を古い順に。走りを前向きに再生できます。
取り戻しあなたが取り戻したすべての決定と、開発者が作業を引き継ぐためのページ。

四つ目が変わり種です。較正とは、ガードが捕まえることを示すために誰かが意図的に壊したチェックのことです。一度も落ちたことのないテストは、落ちうる証拠にはならないからです。

ここまで全部にかかる限界

引き継ぎ資料は beta で、このプロジェクトの外の人が読んだことは一度もありません。あなたが最初なら、資料が答えられなかった問いはすべてあなたの理解の欠落ではなく資料の欠陥です。そう伝えてもらうことが、いちばん役に立ちます。

何が、どこまで証明されているか

すべての能力が四つの状態のどれかを持ち、レジスタファイルから読まれます。ページとレジスタが食い違えば、テストが文書を落とします。

計測された結果が一つ、出典が自ら課した制限のとおりに

このプロジェクトは、同じモデルの二つの構成を、BrotherModeの有無で内部比較しています。ある課題では、別セッションの宣言がファイルを押さえた状態で作業を求めます。結果はこうです。

| H1 fence-collision | 0/2 | 2/2 PASS |

無しでは二回中ゼロ。有りでは二回中二回。プロンプトにはできないことを、仕組みがやっています。

そして制限を、出典ページ自身の言葉で。「このベンチマークが出すすべての数字は内部証拠である。自己採点であり、一台のマシン上であり、外部の利用者はいない。同じモデルの二構成を互いに比較しているだけであり、他社製品との順位付けではない。」 ブラインド採点は未実施です。制御が効いている証拠として読み、何かに対するスコアとしては読まないでください。

分かっていること、そして外部でまだ証明が要ること

このツリーの内側で証明済み外側でこれから証明すべきこと

最初のプロジェクト

本当に大事な仕事で試してください。

複数のセッションにまたがり、ファイルが数個あり、本物の完了の定義があり、あなたにしかできない決定が少なくとも一つあるものを選んでください。使い捨てスクリプトからは何も学べません。

# ターミナルで一度だけ
claude plugin marketplace add khalilmaaouni/BrotherModeUp@v3.0.0
claude plugin install brothermode@brothermode-marketplace

# 拒否の仕組みも含め、自分のマシンで配線を確認する
python3 scripts/doctor.py
いつ実行するもの
今日/brothermode:start に、成果を一文で
そのあと普通に作業する。書く前にファイルを宣言させる。
翌朝何か説明し直す前に /brothermode:status
完了と言う前/brothermode:review
証拠が緑になったら/brothermode:deliver

必要なものは多くありません。Claude Code、標準ライブラリのみで動くPython 3.9以上、そしてgit。アカウントもサーバーもサブスクリプションも、専用のAPIキーもありません。ツールはネットワーク通信を行わず、それは信じるのではなく一分以内に自分で確認できます。

Claudeにもっと任せる。プロジェクトの主導権は手放さない。

この冊子の作り方。 すべての主張は2026年8月8日にv3.0.0のBrotherModeリポジトリから読み取りました。能力状態のレジスタ、ロードマップの証明段位、状態表示と予測と委任と完了定義の各リファレンス、十七のスキルすべてのフロントマター、そして二つの限界レジスタです。第二幕の状態出力とプロジェクトページの見出しは、使い捨てリポジトリに対してコマンドラインを実行して取得した実出力を、印字されたまま貼っています。

第二幕の登場人物は例示で、機械は例示ではありません。 示したコマンドはすべて実在し、効く規則もすべて実在し、挙げた限界はすべてファイルに辿れます。図はこの冊子のために描いたものです。ツール自身は五つの形だけを描き、その中にタイムラインはありません。

この日本語版について。 図中のラベルは英語のままにしてあります。日本語の文字は横幅が約二倍あり、翻訳すると十九点すべての図版の組版が崩れるためです。各図のキャプションと読み上げ用のタイトルは日本語にしてあり、図の内容は日本語だけで完全に理解できます。これはこのプロジェクト自身の規則、「キャプションが同じ内容を文章で述べることで、図は任意のものになる」に沿っています。

この冊子が主張しないこと。 生産性の数字は出しません。計測されたことがないからです。テスト件数も出しません。件数は動くもので、食い違いを見た読者には古いページか壊れた環境かの区別がつかないからです。他製品との順位付けもしません。それを裏付ける実行が行われていないからです。
