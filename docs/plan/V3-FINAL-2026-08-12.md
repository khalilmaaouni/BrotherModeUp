## 1. What ships tomorrow

V3 Final is a repositioning release plus a surface cut plus one small
lifecycle feature, landed on top of an engine that is already green today.
Nothing in the engine changes shape: no schema migration, no new command
category, no new subsystem. What changes is what the project says about
itself (README, the public command list, SECURITY.md) and one small,
already-scoped gap in data handling (a dry-run for purge, a plain-language
list of where your data lives). The category is "verified delivery layer
for AI agents." The launch line is "the reliability layer for serious
Claude Code work." The tagline is "From intent to verified delivery." The
supporting line is "Resume the work. Control the execution. Prove the
result." Every one of those four lines is copy, not a code claim: they land
in README.md and nowhere else, and every existing claim they touch keeps
its own test.

## 2b. REPLAN, decision D10, taken 2026-08-11 night

The founder's instruction, verbatim in intent: do not wait for tomorrow,
start tomorrow's work now. This section replaces the schedule and the
ownership model below it. Nothing about the scope, the files, the
done-checks, the gates or the founder gate changes; only who does the work,
in what order, and on what clock.

**Ownership changes from two builder agents to one writer.** The founder's
standing session rule is that subagents are not dispatched unless he asks,
and he has not. So both lanes are executed by this session directly,
sequentially. The two-lane cap is not breached because two lanes are not
running: one writer moves through both lanes' tasks in a fixed order. Every
done-check named per task still runs after that task's last edit, and no
task closes on another task's evidence.

**Order changes from parallel to risk-first sequential.** The reason is that
a sequential run has no way to absorb a late failure by borrowing another
lane's slack, so the tasks most likely to fail go first, while there is
still room to use the de-scope contingency already written in section 5:

1. B1 purge dry-run, then B2 data locations, then B3 verify skill. The code
   slice leads because it is the only work that can genuinely stay red, and
   section 5 already pre-declares that it de-scopes to the next tranche
   after two failed fix attempts. Discovering that at the end of the night
   would leave no time to act on it.
2. A3 SECURITY.md next: smallest, highest confidence, no dependency.
3. A1 README repositioning.
4. A2 the six-name public surface last among the content tasks. It is the
   largest and touches seventeen files, and it is the one whose failure mode
   is a docs assertion turning red rather than a hard error, so it is the
   safest to be holding when the clock runs out.
5. G3 version and changelog, then G2 checksums, then G1 the full battery.
   G1 runs ONCE, at the end, on a clean tree. Two runs were spent tonight
   discovering that a tracked file written while the battery runs makes it
   refuse to report green, so nothing tracked is written between its launch
   and its verdict.
6. G4 stays exactly as written: the founder's own click.

**What the compression costs, stated rather than discovered.** A sequential
run has no second pair of eyes on its own work, so the adversarial review
that two lanes would have given each other is absent. The gates are
unchanged and none is weakened, but the de-scope contingency in section 5 is
now more likely to be used, not less. If it is used, that is a recorded
outcome and not a failure.

**What is NOT pulled in.** The two defects found tonight (the released
sibling build missing `review-route`, and record creation leaving the health
check red until a checkpoint runs) are decision D9 and remain founder-gated.
They are not silently added to this release. If the founder says yes they
become B4 and B5 with their own done-checks.

## 5. Risks and contingencies

Every contingency below preserves the ship date and every gate; nothing
here is a plan to skip a check.

**Risk: docs tests assert README claims, so the A1/A2 rewrite could
overclaim and turn a currently-passing assertion red.** Contingency:
narrow the wording until the test passes again; never delete or weaken a
test to make an overclaim fit. If a genuinely new claim needs a new
assertion, that is a separate, explicitly flagged addition to
tools/test_bm_docs.py, never a silent removal of an old one.

**Risk: B1 or B2 stays red after two fix attempts.** Contingency,
pre-declared now rather than decided under time pressure later: the code
slice (B1 and B2) moves to the next tranche, and lane A ships alone
tomorrow. This is a deliberate de-scope, decided here, not a discovery
made while writing the delivery packet. It holds the ship date without
weakening G1, G2, G3, or G4 in any way; B3 (the verify skill) is
documentation-only and ships regardless of B1/B2's outcome, since it
depends on neither.

**Risk: the tag or the release happens without the founder.** Contingency:
it cannot. G4 is a hard floor. No amount of A/B/G1/G2/G3 being green
changes who runs the two commands in section 3's G4. If every other gate
is green and the founder is not available, the release sits at "ready,
tag pending," not "shipped."
