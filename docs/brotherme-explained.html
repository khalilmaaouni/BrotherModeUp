BrotherME for Claude Code

A careful project partner, explained simply

You describe what you want in plain words. BrotherME agrees a plan with you, does the work through the right helpers, and only calls something done when a real check has passed after the last change.

What it actually is

Claude Code out of the box is a very capable worker that waits for instructions. BrotherME turns it into a careful colleague. Before building anything, it agrees the goal and direction with you. While working, it tells you what is happening in plain language, keeps a written record of decisions and progress that survives crashes and restarts, and brings you bad news first. And when it says something is done, that claim is supposed to come with proof: a check that ran after the last change and passed. On Claude Code that rule is backed by mechanical gates, and those gates fail open rather than lock you out, so it is a strong default, not a guarantee.

You never need to learn the machinery. If you can describe what you want and answer a few plain questions, you can use it.

Using the loops well

Under the surface, every piece of delegated work runs through the same loop you just watched: the strongest model plans and judges, cheaper and faster models do the labor. Three things make that work well for you.

Let the cheap helper do the labor, and judge the result by the check, not the prose. A confident paragraph is not proof. A check that ran and passed is.
If a helper fails its check twice, the work moves up a grade on its own, with the failure attached. You do not have to notice, and you do not have to ask.
Your job is decisions. Its job is proof. When taste is needed, it comes to you with one recommendation. When a claim is made, it has to survive a check first.

A small ask and a big build

Ask for one small thing (rename a file, draft one email) and BrotherME takes the shortest path: no ceremony, no paperwork, the change and its check. The rules wake up only when the work gets heavy, and that is deliberate: the machinery scales with the ask.

An ambitious build is where it earns its keep. Picture a real product: an app, a website, a data pipeline behind them, copy in three languages, worked across weeks of sessions. That shape is exactly where AI work usually falls apart: one session forgets what the last one decided, two parallel efforts overwrite each other, confident summaries hide failures, and by week three nobody can say what was actually verified. Each of those failure shapes has a named counter here: written state that survives any crash or restart, one writer per file enforced by a gate, parallel helpers behind separate walls, forecasts that are ranges and get corrected by actuals, and a delivery rule that refuses the word done without a passing check. On a one-hour task you barely notice these. Across a three-week build, they compound into the difference between shipping and starting over.

What makes it different

Seven mechanisms. For each: what it does, how you use it, when it matters. This section is kept current by rule: any release that changes a feature updates this section in the same change.

The guided loop

The strongest model plans and judges; cheaper helpers execute; a helper that fails its check twice is replaced by a stronger one.

How to use itAutomatic on any delegated work. Ask for the advanced view if you want to see the routing.
When it mattersAny project big enough to hand pieces away. It is why big builds get top-grade judgment without paying top-grade prices for routine labor.

One writer per file

Before anything writes, its claim on those files is written down, and a mechanical gate refuses a second writer while the claim lives.

How to use itAutomatic. Ask who is working on what to see the live claims.
When it mattersThe moment two things are in flight at once. It is the reason parallel work is safe here and a free-for-all everywhere else.

Proof or it is not done

Done requires a check that ran after the last change and passed; delivery fills a written packet with the evidence.

How to use it/brotherme-review checks work in progress; /brotherme-deliver refuses to close without proof.
When it mattersEvery handoff. It is the standing guard against confident nonsense.

Honest forecasting

Every estimate is a range with a confidence level and the assumption most likely to move it; actuals feed the next forecast.

How to use itIt arrives inside every plan and status. Ask how long at any moment.
When it mattersDeadlines, budgets, and the decision to start at all.

Memory that survives

Decisions, progress, and open questions live on disk, in your project folder and a private records folder, and work is saved right before the AI's memory gets condensed.

How to use itAutomatic. After any crash or restart, /brotherme-status reads the thread back.
When it mattersAny work longer than one sitting. It is why week three still knows what week one decided.

Rules that stick

Correct it once in plain words and the correction can become a stored rule, retrieved before similar work; hard rules act as gates, and turning a correction into a rule always requires your explicit yes.

How to use itSay the correction. It will offer to keep it; you approve or decline.
When it mattersAnything you never want to explain twice, from never publish without my say-so to always show me two options.

Decisions through you, one at a time

Choices arrive as one question with a recommended option first and the tradeoff stated, never a wall of text.

How to use itAutomatic register. Answer the card; work continues.
When it mattersAlways. It is how a non-technical owner keeps real control without reading logs.

What it is good at, and what it is not

Good at

  • Turning a plain-words idea into a checked, delivered result
  • Scoped building: websites, reports, data cleanups, prototypes
  • Catching its own failures: separate checkers try to break the work
  • Surviving crashes: progress and decisions live on disk, not in memory
  • Saying no: it is built to refuse calling unproven work done, with that refusal enforced on Claude Code only

Not good at

  • Pure taste calls: it recommends, but your eye decides
  • Work with no possible check: if nothing can prove it, it says so
  • Anything needing your accounts: payments, sign-ins, publishing credentials stay with you, and it hands those moments back
  • Real work of any length: every result so far comes from test suites and simulated projects, not from a day of anyone's actual work. You may be the first.
  • Unattended runs: nobody has left it working alone for long, and it is not claimed to survive that
  • Being fast on tiny tasks: the checking adds minutes, for a one-line answer, ask plain Claude

Who it is built for, three people deep

Three personas, from no technical background to plenty. Told with the same honesty as everything else on this page: these are designed-for stories, and none of these people exists as a customer yet.

The first-time founder

No technical background, runs on plain words and trust that has to be earned.

Their deep caseThe bakery story above is their story shape. They type /brotherme-start, describe the outcome, answer three questions, approve a one-page brief, then decide only when a decision card arrives, one at a time with a recommendation first. They never meet a technical term unless they ask. When they come back after a week away, /brotherme-status reads the whole thread back in eight plain lines.
What carries themProof or it is not done, decisions through you, honest forecasting, memory that survives.

The ambitious founder with several irons in the fire

Seasoned, impatient, delegating hard, running more than one project at once.

Their deep caseA product rebuild in four lanes at once: the app, the site, the data work, the launch copy. Each lane runs behind its own wall, so four parallel efforts cannot overwrite each other; the guided loop sends bulk labor to cheap helpers while judgment stays on the strongest model; every morning starts with one /brotherme-status view instead of four scrollbacks. When they correct course once (never announce a launch before legal reads the copy), that correction is offered as a stored rule and resurfaces on every future launch as a gate. When a contractor joins in week two, the deep tour behind /brotherme-help generates the where-do-we-stand page that replaces a day of onboarding calls.
What carries themThe guided loop, one writer per file, rules that stick, the deep tour.

The seasoned builder

A developer or technical individual contributor who wants to write code alongside it, not watch from the passenger seat.

Their deep caseThey join mid-project and take the deep tour: the live code map, the data model, every decision with its reasoning. Then they claim the module they want to write by hand, and the same gate that keeps two helpers from colliding now keeps helpers out of THEIR files while they work in their own editor. Their code lands under the same law as everyone else's: tests beside the code, a check after the last change, review by a reader who did not write it. When they want to extend BrotherME itself, the co-build section shows the house conventions: mirror the closest sibling file, give every risky call an explicit failure path, keep the seam small.
What carries themOne writer per file shared between humans and helpers, proof or it is not done, the deep tour.

Install it, and keep it updated

Open Claude Code and type these two commands, one at a time:

/plugin marketplace add khalilmaaouni/BrotherModeUp
/plugin install brotherme

If Claude Code asks which source to install from, pick the one you just added, and restart if it tells you to. That is the whole install. To check it worked, type /brotherme-help. To remove it later, type /plugin uninstall brotherme; your projects and records stay untouched.

To update, the path depends on how you installed it. If you used the plugin, type these two lines:

/plugin marketplace update brotherme-marketplace
/plugin update brotherme

Then restart Claude Code. Or skip the two lines entirely: type /brotherme-update. It checks your version against the newest release and walks you through updating, in plain words.

If instead you cloned the repository, update it inside the skill folder:

git fetch --tags
git checkout <newest tag>

The seven commands

/brotherme-startBegin a project. It asks what you want to accomplish and turns your answers into a one-page project brief you approve before anything is built.
/brotherme-statusWhere things stand: goal, progress, time remaining, any decision waiting on you, and the evidence behind each claim.
/brotherme-nextThe single best next step, with a reason and an honest time range.
/brotherme-reviewChecks finished work against a written definition of done, point by point, and never softens a failing point.
/brotherme-deliverWraps up. Delivery requires proof; without a passing check it tells you plainly what remains instead.
/brotherme-helpExplains what you have and what to do next, in plain words.
/brotherme-updateChecks your version against the newest release and walks you through updating, in plain words.

Honest limits, before you rely on it

  • This is release candidate 2.0.0-rc.11, not a finished 2.0.0. No day of real founder work has yet gone through it: everything here rests on test suites and simulated projects. The remaining step is someone using it on live work, and that has not happened yet.
  • The two-line install above has been through its full cycle exactly once, on the author's machine. You may be the first person to run it from GitHub. If it misbehaves, the repository's issue page wants to hear about it.
  • It is verified on Claude Code only. Other AI coding tools get advisory files, not enforced guarantees.
  • Use one install path, not both. The plugin and the older clone-based install wire the same automation; a machine carrying both runs everything twice.
