## What lives here

Every subdirectory of this folder is one handover pack, named
`<YYYY-MM-DD>-<slot>` (slot defaults to `session`). A pack is generated by
`tools/bm_handover.py skeleton` and holds seven files, always in this order:

1. `00-READ-ME-FIRST.md`: read order, and a pointer to the `bm_lead.py
   handover-pack` ledger pages when one exists (this pack does not
   duplicate them).
2. `01-HANDOVER.md`: which records (fences) this session held, at what
   state, plus the decisions and unacknowledged handovers the store
   already recorded, and the narrative of what happened and what is next.
3. `02-LEARNINGS-AND-MISTAKES.md`: learnings, mistakes, and near misses.
4. `03-RULES-AND-PROCESS-FIXES.md`: a rule or process fix this session's
   own mistakes surfaced, if any.
5. `04-NEXT-LOOPS-PRIORITIZED.md`: the next loops, in priority order.
6. `05-VAULT-AND-OBSIDIAN.md`: what changed in the Kay Vault, and its
   session log entry.
7. `06-CLOSE-REPORT.md`: opens with a line starting with the exact word
   FINISHED, or the exact word UNFINISHED and exactly where the baton
   lies. `verify-close` refuses to pass without this line.

A copy of `docs/plan/COMMAND-CENTER.html`, from the moment the pack was
generated, is included as `COMMAND-CENTER.html` when that file exists.

Each of the seven files carries exactly one narrative slot, marked
`FILL-BY-HAND` between `<!-- bm-human:begin -->` and `<!-- bm-human:end -->`
markers. Everything else on the page is generated from the store and is
safe to regenerate; the human block survives regeneration byte for byte
(I10: generated output never destroys human text), so re-running
`skeleton` over a filled pack never loses what a person already wrote.

## The ceremony, in one line each

CLOSE, before a session ends: refresh the pack (`skeleton`), fill every
`FILL-BY-HAND` slot by hand, park every record this session holds with a
handover (`bm_store.py park ... --handover "<heading>"`), commit the pack
folder, zip it (`bm_handover.py zip`), update the Kay Vault session log,
then run `bm_handover.py verify-close` and quote its verdict. A FAIL means
the ceremony is not done.

START, before new work: run `bm_handover.py detect`, read the newest pack
in its stated order, acknowledge consumed handovers (`bm_store.py
handover-ack`), adopt or park every dead-session leftover `detect` names,
then open this session's own work record.

The full rule text is docs/superpowers/specs/2026-08-11-baton-ceremony-design.md,
section 3.

## The tool

`tools/bm_handover.py`, Python 3.9, standard library only, no network, no
subprocess. Four commands:

- `skeleton [--out DIR] [--slot NAME] [--date YYYY-MM-DD]`: writes or
  regenerates a pack.
- `verify-close [--pack DIR] [--session ID]`: the mechanical checklist
  above. NO-DATA when there is no store or no pack to judge; PASS only
  when every check clears.
- `zip [--pack DIR]`: packages the pack to
  `~/Documents/BrotherModeUp-handovers/BrotherMode-Handover-<date>-<slot>.zip`.
  Idempotent by content: an unchanged pack says so rather than rewriting
  the file.
- `detect`: read only. Reports the newest pack and zip with their ages,
  unacknowledged handovers, and dead-owner leftovers (via
  `tools/bm_stall.py`'s own sweep), each with the exact command that
  clears it. Exit 0 always; an empty estate is stated, never silent.

Every store read goes through a public `bm_store.py` or `bm_stall.py`
function (`ReadOnlyStore.dump()`, `bs.verify()`, `bm_stall.sweep()`); this
tool writes no SQL of its own and never writes the store. The store
mutations the ceremony needs (`park`, `handover-ack`) stay in
`bm_store.py`, exactly where the rule sends the founder.

Tests: `tools/test_bm_handover.py`.
