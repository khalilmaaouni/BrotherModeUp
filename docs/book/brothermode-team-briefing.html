Act one

The problem, and what we decided to do about it

Four short sections. What went wrong, where we are going, what we believe, and how the thing is built. Then the story starts.

The Thursday that started it

Two agents were working. One was refactoring a pricing module. The other, launched twenty minutes later by somebody who did not know the first was running, was adding a field to the same file.

The second one finished last. It wrote the whole file from its own copy.

Ninety minutes of work was gone. Not corrupted, not conflicted, not flagged. Gone, and the session that destroyed it reported success, because from where it stood the write had worked perfectly.

Nobody noticed until the next morning.

That is the founding scene, and it is not the only one. Four more like it are written down, one file each, in the folder this project keeps for mistakes. Every rule in BrotherMode traces back to one of them.

Where this is going

The destination is an autonomous product team: workers that carry an outcome from a sentence to a shipped, checked result while you sleep.

That is the direction. It is not the claim.

What is proven today is narrower, and the repository's own front page says so in those words: memory, guardrails and proof, each with its evidence named. The founder chose that narrower headline on 7 August 2026 over a broader one, because three independent reviews said the broader one ran ahead of the evidence.

Hold us to the narrow version. The wide one is where we are walking.

README.md lines 10 to 15 state both the vision and the reason the headline was narrowed.

Five beliefs, and each one cost us something

A rule in a prompt is not a control

You can write "never overwrite another agent's work" at the top of every prompt and Thursday still happens, because the thing you are instructing is also the thing deciding whether to comply. A control is a check that runs. So the single-writer rule is a Python program on a hook that returns a refusal before the tool call executes. Not a request. A refusal.

Done is a command, not a feeling

Evidence gathered before the final edit proves nothing about what is being delivered. So done means one thing here: a verifying command ran after the last change, it passed, and its output is quoted. No command, no done.

The record outlives the session

Sessions die constantly. Context fills, a laptop sleeps, a process is killed. If the plan lives only in the conversation, the death costs you the day. So decisions and open work go to disk, and the whole working tree is snapshotted right before context is compacted. Dying should cost minutes.

Bad news first, always

The most expensive thing an assistant can do is perform confidence it has not earned. Failures lead every report. Estimates arrive as ranges with a confidence, never a number somebody will hold you to. An unverified figure carries the word unverified next to the figure. A limit you can read beats a feature you cannot check.

Ceremony is a cost, and it is scored

Five subagents at a one-line question is not thoroughness, it is waste, and this system logs it as a failure called overthought. One blind pass at a full audit is logged as underthought. Proportion is a rule, not a mood.

Monday, 09:10

Ten minutes to install, and one minute to trust it

Tomas installs it, because Tomas is the one who will be asked what it does to the machine.

Two lines in a terminal. No account, no server, no signup, no API key of its own.

claude plugin marketplace add khalilmaaouni/BrotherModeUp@v3.0.0
claude plugin install brothermode@brothermode-marketplace

The @v3.0.0 matters: it pins to the released tag rather than a moving branch, so the code that will run automatically on every future session comes from a fixed, checkable snapshot.

The whole path runs on every release inside a throwaway configuration via scripts/release-smoke-install.sh: marketplace add, install, version matched against VERSION, every hook group registered, clean uninstall. A release whose smoke run does not print PASSED does not ship.

Then Tomas does the thing that actually earns trust, which is not reading the README.

python3 scripts/doctor.py

Ten read-only checks. The deepest one builds a throwaway project, has one imaginary session claim a file, has a second one try to write it, and shows Tomas the refusal happening. Not described. Happening.

Tomas also checks the network claim rather than believing it:

grep -rnE "^[[:space:]]*(import|from)[[:space:]]+(urllib|http|socket|requests)" tools/*.py
# expect no output

No output. And the ban is enforced by a test on every shipping module, so it cannot regress quietly.

What just got wired to the machine

Six programs, on six moments in a session's life. Five of them watch. One can say no.

Tomas asks the right question, and gets an honest answer

"Can it stop a shell command?" No. The refusal covers the editing tools and a readable patch envelope on the shell leg. A plain echo into a claimed file is detected afterwards, not prevented. There is no container and no operating system sandbox here. Hooks are cooperative enforcement, and if that is not enough for your surface, this is the moment to say so.

Monday, 10:00

The first sentence, and the first decision

Maya types one sentence. Not a ticket, not a spec. A sentence.

sync on reconnect, and show the user which state they are in.

What comes back is not a plan. It is a short conversation that asks only the questions whose answers change the scope, one at a time, recommended option first. Then it writes a brief and puts one decision in front of Maya.

Maya picks one. The choice is recorded with its alternatives and the condition that would flip it, which matters on Thursday when somebody asks why.

Underneath, the week has just entered a loop it will not leave until Friday.

A smoothed-over sentence would carry less information than any one of those gaps.

The five shapes, and nothing else is ever drawn

This is the part most people underestimate. The page does not draw whatever looks good. Five shapes are allowed, each answering exactly one question a human actually asks, and a sixth shape is refused where it is built rather than discouraged in prose.

Every label is a noun phrase plus a status word, exactly as the rule requires. Exactly one pipeline node says NOW. Every bar carries its raw number. And where a limit has not been agreed, the bar says no limit agreed yet rather than drawing a full bar against an invented ceiling.

One naming detail, so you do not think this page lied to you

If you grep the generated file, the second drawing carries the internal element id bm-timeline. It is not a timeline. It has no dates, no durations and no time axis: "stage 7 of 10" is a position in the ten-state task lifecycle, not elapsed time. The id is a legacy name for what the law calls the lanes shape, and the title it prints on screen, "How far each lane has moved", is the accurate one.

Why there is no gantt chart, and why that is a feature

The rule is written in one line in references/visual-surface.md: "There is no pie, no gantt, no timeline, no diagram of the code or the data, and no shape with no record behind it."

The reason is the one above it: every node and bar on any surface is computed from the project's own records, and nothing is hand drawn or kept in step by somebody remembering to. A gantt bar implies a start date, an end date and a duration with a precision the records do not have. Drawing one would mean inventing three numbers per row and putting them on a picture people trust more than prose.

So the tool draws what it can prove and refuses what it cannot. The bars in the counts shape above are the exception that proves it: they carry raw numbers written on them, because a bar without its number is a shape asking to be misread.

references/visual-surface.md, the five shapes table and the line that closes it. The diagrams elsewhere in this booklet are illustrations drawn for the book, not output from the tool.

And the ladder that decides whether you are interrupted at all

references/visual-surface.md defines the four surfaces, the five shapes and the four levels. tools/bm_visual.py computes the levels as one function over rows with no table behind them, and tools/test_bm_visual.py holds the four anti-noise rules to that.

Wednesday, 11:20

Two people reach for the same file

Sam is halfway through the status banner. Tomas, in another window, decides the sync engine needs a change in the same shared module.

On the old Thursday, one of them would have lost the morning.

The claim itself was written before Sam's work began, never after, and it names the objective, the exact files, the boundaries, the termination condition, the declared effort tier, and a runnable check on the outcome. A new claim must be disjoint from every live one. Overlap means queue, never parallel.

There is deliberately no expiry timer. A law promising a lease that expires while no code expires anything is worse than no law. A claim is released by an explicit park, complete, adopt or transfer, and a dead session's claim is adopted at close by the coordinator, never by a clock.

The rule that catches the coordinator too

Added after the coordinator wrote claims for three workers, dispatched them, then edited four files of its own with no claim for itself. Nothing collided, which was luck. When any worker is live, the coordinator's own files get a claim too. Being the one who writes the registry is the reason to be in it, not an exemption from it.

Wednesday, 15:00

The front-end half, and the loop that catches what reading cannot

Sam finishes the offline banner. It compiles. The CSS reads correctly. Every instinct says ship it.

This is the single most common way front-end work goes wrong with an agent, and the rule for it is one sentence long. Verify by looking at rendered output, never by reading code. Reading the code and concluding it looks right is a named violation, not a shortcut.

Thursday, 09:15

The check that fails, and why that is the good day

Everything looks finished. Maya asks the obvious question, and this is the one command in the product that exists to disappoint you.

/brothermode:review

Fifteen points, applied one at a time, each carrying the evidence that proves it or the reason it does not. Failures first. Four of the fifteen are where most work actually fails:

  • Verification runs after the final edit, not before it.
  • A calibration proves the test can fail for the intended defect. A test that cannot fail is not evidence.
  • An independent reviewer evaluates substantial work. The writer and the reviewer are never the same without a stated exception.
  • Remaining uncertainty is stated. Not implied, not omitted, stated.

On Thursday the screenshot gate fails. The banner renders correctly at desktop width and clips its second line on a small phone. Nobody had looked at a small phone.

The work goes back to Wednesday's step. Nothing in this system lets a red check become a green delivery, and there is no flag that makes it.

references/definition-of-done.md carries all fifteen points. Done is never a state a worker declares about itself; it is the result of that checklist passing.

Friday, 10:00

The number that nearly shipped wrong

Priya is writing the launch note. One figure in it matters: how many sessions currently lose their work when the network drops. It is the number that justified building the feature at all.

Data work runs under its own profile, with four roles at the table rather than one, and one rule that bites harder than the rest: every headline number is independently derived a second time before it is shown. Not after somebody asks. Before.

Priya's two routes disagree by a factor of three. The first query counted sessions; the second counted devices. One device, several sessions. The figure that would have gone into the launch note was wrong, and it was wrong in the flattering direction.

Then Friday ends the way the week was always going to end.

/brothermode:deliver

The packet is generated from the records, never filled in by hand, so what it claims and what the store holds cannot differ. It names what was built, every check that ran after the last change, and what was left out on purpose. And it refuses the words ready to deliver unless every acceptance check has evidence produced after the final edit.

When to skip it entirely

Most tools do not write this section. The industry's own standard README template treats a limitations note as optional guidance inside the project description. Here it is structural, because the fastest way to discredit a tool is to use it where it does not belong.

Reach for it when any of these is true

  • The work spans more than one session, so something has to survive between them.
  • More than one agent or session could touch the same files.
  • A wrong number costs money, or a wrong claim costs credibility.
  • The step is irreversible: a release, a migration, a deletion, a publish.
  • Somebody who was not in the conversation will pick the work up later.

Do not reach for it when

  • It is a one-shot question with a self-contained answer.
  • It is a throwaway script nobody will run twice.
  • You are brainstorming, and verification ceremony would kill the momentum.
  • Nobody on your team will ever run the weekly review. The loop is the point; without it you pay the overhead for nothing.

docs/DESIGN.md section 10 states both lists.

And the largest gap, said plainly

This system has been used for real work. It has never been measured on a real project. There is no counted project, no recorded rework rate, and no comparison against working without it. Any productivity number you are ever shown for BrotherMode is invented, including one from me.

Why not just another plugin

A Claude Code plugin can ship skills, custom agents, hooks, MCP servers, language server configurations, background monitors, executables on the shell path, and default settings. That is the full palette available to every plugin author.

Nearly every plugin spends it on capability: more commands, more specialist agents, more integrations. That is a good trade, and it is why the ecosystem is worth having.

BrotherMode spends it on constraint and continuity: one program that can refuse a tool call, and a record that outlives the session. Those are the two things a session cannot give itself, because a session cannot remember what it never wrote down, and cannot be stopped by a rule it is also the judge of.

Named, with one genuine strength each

Every one of these beats BrotherMode at something. Read the middle column as true, not as politeness. Each is a desk assessment read from that project's own public material, because no file in this repository can carry evidence about a codebase it does not own.

Your checklist for choosing, four questions in order

  1. Will more than one session or agent ever touch these files? Yes: you want the refusal.
  2. Will this work outlive one session? Yes: you want the record.
  3. Does being wrong cost money, credibility, or a rollback? Yes: you want the verification gate.
  4. Will anyone run the weekly review? No: use something lighter. The loop is the point.

Four noes means use a lighter tool, and spend the overhead somewhere it buys you something.

Deliberately not on the list

Non-promises, written down so silence cannot be read as a plan. Native mobile builds. Creative media generation. Office document artifacts, because what is generated is markdown and the records behind it, so a delivery packet stays diffable in review. Multi-user and enterprise coordination, which is a design limit rather than a gap.

None of that is a judgement about the tools that do those jobs well.

Where you come in

Four of the six waves cannot be closed by writing code. They close when somebody outside the room uses this and reports what happened.

The four things that would move this furthest, fastest

  1. Run one real project on it and count what happened. Not a demo. A project with a deadline. That is wave four.
  2. Install it on a machine that is not the author's and report the first thing that broke. Waves two and three.
  3. Try to break one claim in this reference. Succeeding is worth more to us than confirming.
  4. Read a handover pack cold and mark every question it failed to answer. Nobody outside this project has done that yet.

Where the truth lives when pages disagree

This booklet is a reading of the repository, not the repository. When something here and something there disagree, the tree wins. In order of authority:

  1. The code and its tests. python3 tools/test_all.py ending ALL GREEN is the strongest claim anyone can make about this system.
  2. capabilities.status.json. The register every capability state is generated from.
  3. docs/KNOWN-LIMITS.md and docs/NOT-FINALIZED.md. What is not proven, and the numbered defect register. Both are believed over the front page.
  4. docs/ROADMAP.md. How far each claim has been checked, and what is coming.
  5. SKILL.md and references/. The law itself, and the files it loads when a situation applies.
  6. This booklet. Last, and happily so.

The deliverable is not the code a worker wrote. It is the code a worker wrote, plus a passing check that ran after the last change, plus a written trail explaining why.What the word proven is doing in the title

How this booklet was built. Every claim about BrotherMode was read out of the repository tree at v3.0.0 on 8 August 2026: the frontmatter of all seventeen skills, hooks/hooks.json, capabilities.status.json, agents/, references/visual-surface.md, references/delegation.md, references/definition-of-done.md, docs/ROADMAP.md, and the two limits registers. Nothing here is quoted from memory of a conversation.

The story is a composite, and the machinery in it is not. Maya, Sam, Tomas and Priya are illustrations. Every command they run, every rule that bites, and every limit named is real and traceable to a file.

Three blocks in this booklet are real tool output, captured on 8 August 2026 by running the offline mode project through brothermode_cli.py against a throwaway git repository outside this tree: the eight-field status, the fifteen section headings of the generated project page, and the node labels of the three drawings that page produced. They are pasted exactly as printed, with no reflowing. The remaining diagrams were drawn for the book, and the two places where that distinction could mislead say so in their own captions.

External sources, each a page actually opened. The plugin component list is from code.claude.com/docs/en/plugins. The four-mode documentation structure is Diátaxis, diataxis.fr, adopted by Django, Canonical, Cloudflare and Gatsby. The honesty structure of the comparison chapter is SQLite's, sqlite.org/whentouse.html. The README convention that treats limitations as optional is The Good Docs Project's, thegooddocsproject.dev/template/readme.

What this booklet does not do. It quotes no test count, because counts move with every test that lands and a reader seeing a mismatch cannot tell a stale page from a broken install. It quotes no productivity number, because none has ever been measured. And it is not held by the documentation suite that holds the repository's own pages, so when it goes stale, it will go stale quietly. Check it against the tree.
