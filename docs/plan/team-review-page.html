Read this first, because it changes the rest

The review was run against an installed build that is generations behind the source: 1.0.0-rc.2 installed, 3.2.0 in the repository. The two heaviest findings, that nothing in the design folder says what the software must do, and that a green gate says nothing about the problems a QC lead actually finds, both have working answers that landed on 15 August, after the review was written.

That is not a reason to discount the review. It is the review’s own argument made a second way: a fix nobody has installed is not a fix, and the version string did not warn anyone. So the first action here is not engineering. It is shipping the current build and asking two reviewers to re-read two items.

What is working, and what it constrains

Four of these are load bearing, so every solution below has to keep them: checks written before the build catch real contradictions in the specification; bad news comes first, with no flattery and no jargon; NO-DATA is a real answer, so absent evidence is never a pass; and every rule names what enforces it, with the parts no software computes marked as such. A solution that is only a sentence in a document is written here as UNENFORCED, in those words.

The problems, one by one

P1Partly answeredthe non-developer reviewer

Setting up is hard without a developer background

Half fixed. The tools are now tested on Windows in CI. The first hour on a fresh Windows machine is unchanged: no installer puts the command on the PATH, and two prerequisites still have to be satisfied alone.

Recommended

A first-run script that installs nothing silently, prints exactly what is missing with the one command that fixes it, and repairs the PATH. Proven by a clean Windows runner in CI reaching --help at exit 0.

  • A doctor command listing what is wrong: cheaper, and useless to someone who cannot run the command in the first place.
  • Remove the prerequisite entirely: largest change, deletes the CI story, filed as a direction rather than a fix.
P2Confirmed openthe analyst lead

The guide describes how analysts work here, incorrectly

The guide says analysts hand over a conversation. They hand over a specification document, with the core acceptance criteria in the ticket. The warning matters more than the error: people stop trusting a document that describes their own job wrongly.

Recommended

Rewrite the section around the specification as the source of context, keeping the real principle: the assistant needs the specification, not the chat.

  • Go further and make the specification the declared input to the behaviour table, so the correction is worth more than an apology.
  • Drop the practice-to-stop list entirely: least effort, loses a real teaching point.
P3Confirmed openthe first-time user, the architecture reviewer

Discussion before planning is not enforced

Confirmed, and wider than reported. Searching the whole repository for any enforcement of a discussion step returns nothing. It was written as an instruction to the model, and an instruction to the model is not a control, which is this product’s own first law applied against itself.

Recommended

Make it a state rather than a sentence: sizing cannot be recorded until a clarify record exists, and the refusal names the command that creates one. This is the only version nothing can silently skip.

  • Detect and report at session close: softer, and it fails toward silence, which is the complaint.
  • Put the questions in the first turn, so skipping is the deliberate act: cheapest, still unenforced, and it changes the default.
P4Partly answeredthe first-time user, the architecture reviewer

The decisions record stays empty while decisions get made

Real, and half owned. Three memory systems run in parallel and none is aware of the others; the built-in one stayed empty for a whole project. The conflict class is at least named now and honestly reported as NO-DATA, because no detector exists.

Recommended

Harvest instead of asking. Decisions already get written, into commit messages and a notes file. Scan that range, propose rows, write only what a person confirms. Nobody types anything twice and the empty table fills from real history.

  • Refuse to close a change whose decision record cites an unexplained alternative: stronger, and it adds an obligation to a team already over-obligated.
  • Name one system the authority and demote the others to pointers: the real fix, and it needs a ratification rather than an engineer.
P5Partly answeredthe first-time user

Hard for a first-time user, and status goes stale after clearing

Three things. The next-command suggestion already exists in the current build. The wall of text is real. The stale status after clearing a session could not be reproduced, and the failure mode it resembles is documented here: four separately written next-action ladders once gave three different answers to the same change.

Recommended

Ask for one reproduction, the commands in order and both outputs, and re-test on the current build first. One message, and it may close the item.

  • If it reproduces: stamp every status line with the commit it was derived from, so an out-of-date answer announces its own age.
  • Short form by default, long form behind a flag.
P6Confirmed openthe architecture reviewer

The check that confirms a check ran grades only the shape

Confirmed, and narrower than it was: evidence produced before the code moved is now refused. What the gate still never asks is where the evidence came from. A hand-written file and a real build run are indistinguishable to it.

Recommended

Adopt the reviewer’s own operating rule mechanically. Evidence records its producer, and strict mode accepts only evidence the build system made. One configuration value in the pipeline sets it. A laptop run still gets a verdict; it just cannot be the one that closes a change.

  • Sign the evidence: stronger, and it needs key handling the team does not have today.
  • Leave it and publish the limit, which by this product’s own rule means writing it UNENFORCED.
P7Confirmed openthe architecture reviewer

The gate never opens the plan that says which checks were owed

Confirmed, with one new exception: a verification plan citing a behaviour rule that no longer exists now fails. The other direction, every owed check appearing in the evidence, is still unchecked, so evidence containing one check passes as green as evidence containing all of them.

Recommended

Close the loop the behaviour table opened: every rule’s proof names a check, and the evidence must contain a check of that name or the gate fails naming the rows it is missing. Cheap, because it reuses a table that now exists instead of inventing a plan format.

  • Adopt the reviewer’s own extra check and ship it with credit: fastest, and it turns a reporter into a contributor.
  • Count and report only, NO-DATA when the plan cannot be read: weakest, honest, never blocks.
P8Confirmed openthe analyst lead, proven on the live change

Ordinary changes are sized as heavy ones

The sharpest finding in the review, and it is four lines of code. Answering yes to the contract question alone produces the heavy tier, with no other answer needed. Crossing a service boundary alone does not. On an architecture where nearly every change touches an API contract, one question decides the ceremony for everything.

if sensitive or not reversible_within_an_hour:  T3
if changes_contract or consumers == "many":    T2   <- one question, on its own
if crosses_boundary or consumers == "some":    T1
otherwise:                                     T0
Recommended

Split the contract question in two: additive or breaking. Adding an optional field no existing consumer reads is not the same risk as changing what a field means. Additive with few consumers lands one tier lower; breaking stays where it is. The live change re-sized is the done-check.

  • Let the diff answer instead of the person, derived from the API schema: more accurate, much more work, NO-DATA where no machine-readable schema exists.
  • Keep the tier and cut what it costs: same felt outcome, and it weakens what a tier means.
P9Closed in sourcethe architecture reviewer

Nothing in the design folder says what the software must do

Called the largest gap, and answered on 15 August in a build the reviewers did not have. There is now a behaviour table, required from the second tier upward, reading ID | Starting point | Trigger | Required outcome | Proof, and the check behind it refuses four distinct ways to fake it: a rule with no agreed proof, rows that are still the shipped example, a verification plan citing a rule that was deleted, and an unreadable table, which fails rather than passing quietly.

One clause of the finding stands: it does not say who writes the table. The observation behind it stands too, that the one step with no tooling is the step where behaviour is defined.

Recommended

Ship the current build and ask the architecture reviewer to re-audit this one item. No engineering, and it turns the biggest open finding into either a close or a much sharper reopen.

P10Confirmed openthe architecture reviewer, the analyst lead

Nothing handles a requirement changing

Confirmed open, and the most structurally serious item here, because it gets worse with time rather than staying constant. No design version, no way to mark one superseded, no staleness clock. A design describing an intention abandoned two months ago stays green indefinitely. From the other end: developers find edge cases during coding, the specification changes, and the proof list written early has to be revisited instead of testing what is ready.

Recommended, and smallest

A staleness clock with no new concepts. A design records the commit it was written against, and once the code has moved past it, checks report NO-DATA with a stale-since line. NO-DATA rather than a failure, because a stale design is an unknown, and an unknown must never read as a pass.

  • Supersession as a link, so a design can name the one it replaces and status refuses to read a superseded one as current.
  • Re-size on churn, not risk alone: if the change grew past a threshold, recompute and report the delta.
P11Confirmed openthe whole team, on the live run

The step called PROVE checks the paperwork, not the work

Confirmed. Everyone assumed it compares what was built against what was designed. It checks that documents exist, are not empty, and that certain evidence files are present. The comparison is a different command the step never runs, and it never looks at review findings at all.

Recommended, and it is documentation, not code

Re-describe the step as a completeness check, name the comparison command beside it so it actually gets run, and move the step off QC and onto the engineer, because what it checks is whether the engineer produced the documents they owe.

  • Have the completeness step invoke the comparison itself, so neither verdict can be skipped by not knowing about it.
  • Give QC’s real question a tool of its own, which is the exploratory sheet in P14.
P12Partly answeredthe whole team

We use Bitbucket, not GitHub

Shipped on the orchestration side and now standing law: GitHub canonical, Bitbucket first class, with a full pipeline definition and honest UNVERIFIED labels where a leg has not been observed. Open on the assurance side, whose approval and pipeline steps are still worded in GitHub terms. One blocker sits outside the code entirely: the test workspace is read-only because it exceeds its user limit, so that half of any two-host check is BLOCKED rather than merely unverified.

Recommended

Port the two-host pattern across: host-neutral scripts, one thin pipeline definition per host, and any host-specific command reporting NO-DATA naming the host rather than erroring or passing quietly.

  • Make the approval check host independent: a signed trailer verified locally beats any provider API and works identically on both.
  • Decide first, build second, which is what the team actually asked for.
P13Confirmed openthe architecture reviewer

Fifty point-in-time designs after a year, none describing the system

Confirmed, and it is P10 observed later. Nothing merges, supersedes or indexes designs, so a newcomer reads fifty of them in no particular order to reconstruct a system nobody ever described.

Recommended

Supersession links plus one command that walks every design and prints the current behaviour rules across all of them, newest winning and conflicts named. A system description assembled from what exists is the only version that survives, because nobody has to maintain it.

  • A living system document every change updates: better to read, and it reintroduces the maintenance burden that made the first one go stale.
  • Accept it and say so, which is what happens today by default rather than by decision.
P14Closed in sourcethe analyst lead, the QC lead

The question nobody could answer

The QC lead will not accept against a numbered criteria list, because what she finds is unnatural behaviour, interface problems once she is hands on, misunderstandings missed during design, and awkward text where the translator lacked context. None of that is an acceptance criterion, so a green gate systematically under-represents how much checking remains.

The tooling half landed on 15 August. The behaviour table becomes the tester’s own working sheet, one case per rule, plus an exploratory tail whose first charter is named unnatural-behaviour: the software does something nobody asked it to. A filled sheet reads back, and drafts new behaviour rules from what was found, so a discovery becomes a rule for next time instead of a comment on a ticket. Deliberately, none of it is a gate: the moment exploratory testing becomes a gate it stops being exploratory.

Recommended

Run the sheet once on the live change and ask the QC lead the only question that matters: did it catch what she would have caught anyway. That answer is the acceptance test for the whole idea.

  • Print what was NOT examined, by name, on every all-green summary: regression, cross-device, performance, interface. The cheapest way to stop a green verdict from lying about its own scope.
  • Measure the queue before and after, and publish the delta whether or not it moved.
P15Not oursnamed, never gated by the tool

The part no tool fixes

QC verifies far more slowly than developers now build with an assistant. That is a capacity fact, not a defect, and writing a proof list earlier adds a step without removing the bottleneck. The honest posture is to measure it, reveal it, remove labour that feeds it, and never add an obligation and call it a fix. The only measure that decides whether any of this worked stays the team’s own queue numbers, not a gate verdict.

Knowing when to stop and ask

A separate ask, and it is built rather than described. Three partial answers already existed: an automated controller that gives up after two failures, a sentence in a worker brief, and two watchdogs that notice a stuck machine. None of them noticed a stuck line of reasoning. Nothing counted that the same objective had defeated three different methods.

There is now one small tool that records attempts and answers one question, continue or escalate.

TriggerFires whenWhat it means
forcing conditiona named danger is recorded, at zero attemptsguessing is the risk, so no number of tries changes the answer
approaches exhaustedthree distinct approaches have failedthe problem has beaten the methods this session can name
no new informationtwo failures share one observed root causethe second attempt bought nothing, which is the real signal
budget spenta declared attempt budget is gone with nothing passingthe work was sized and the size was wrong

Never on a single failure, with one exception: a failure affecting what the system reports as true escalates immediately, because a wrong status standing longer is the whole cost. When it escalates it prints who is being asked, what it found, its recommendation, the alternatives it has not tried, the risk if it guesses, the one decision it needs, and what it will do if nobody answers. It refuses to print that without a recommendation and a default action, because handing a person a problem with no proposal moves the work without reducing it.

It never answers the question itself, never retries on its own, and never decides for the human.
