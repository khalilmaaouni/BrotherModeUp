The philosophy, before the chapters

Every chapter in this book is an application of one uncomfortable belief, so the belief deserves its own page: an AI's confidence is not evidence, and a rule written in a prompt is not a control. Anyone can tell a model to be careful, to double-check, to never overwrite work. The telling costs nothing and changes little, because the model that forgets your file also forgets your instruction. Every mechanism in this project exists because somebody took that belief seriously and asked: what would this rule look like if it did not depend on being remembered?

The answer, each time, is one of two shapes. Either the rule becomes machinery (a gate that refuses, a test that fails, a hook that records), or the rule becomes a handover (the risky step is prepared completely and given to a human hand). A rule that is neither machinery nor a handover is listed honestly as discipline, which is the weakest of the three and says so. That three-way honesty about its own rules, more than any single feature, is what makes this project itself.

The ten laws

Stated once, plainly, each with the failure it exists to kill. The chapters that enforce and demonstrate each are named in parentheses.

  • 1. Look before touching. A session maps what is already true (what changed, what is claimed, what is mid-flight) before writing anything, and coordinates with work it finds rather than overwriting it. Kills: the confident session that flattens another's work. (Chapters three, eight, fifteen.)
  • 2. One writer per file. The claim is written before the work starts; a mechanical gate refuses the second writer; the refusal names the holder. Kills: silent overwrites, the way parallel work actually dies. (Chapters three, eight, fifteen.)
  • 3. Proof, or it is not done. Done requires a check that ran after the last change and passed, quoted, and delivery packets carry the evidence. Kills: the confident summary, the cheapest thing a model produces. (Chapters four, six, thirteen.)
  • 4. The guided loop. The strongest model plans and judges; cheaper helpers execute; two failed checks escalate upward with the failure attached. Kills: paying judgment prices for labor, and trusting labor with judgment. (Chapters thirteen, fifteen, sixteen.)
  • 5. Ranges, never promises. Estimates carry a range, a confidence, and the assumption most likely to move them; actuals feed the next forecast. Kills: the point estimate, a lie about certainty. (Chapters four, thirteen.)
  • 6. Bad news first, labels on numbers. A failing check leads the message; a number that could not be independently verified carries its label at the number. Kills: the buried caveat. (Chapters five, sixteen.)
  • 7. The human holds the keys. Decisions arrive one at a time with a recommendation first; anything touching credentials, money, publishing, production, or deletion is prepared fully and handed over. Kills: the automation that quietly outgrew its permission. (Chapters eight, fifteen.)
  • 8. Memory lives on disk. Decisions, progress, failures, and open work are written to plain files (the vault, the state records) that survive crashes, restarts, and compaction. Kills: the project that resets every morning. (Chapters seven, nine, fourteen.)
  • 9. Corrections become law only by consent. A correction can become a standing rule retrieved before similar work, promoted only with the human's explicit receipt, and no learned rule may ever weaken the laws above it. Kills: repeating the same correction forever, and also the tool that rewrites its own constitution. (Chapter five.)
  • 10. Wrong claims are corrected in daylight. A sentence that turns out false gets a dated correction on top, never a silent rewrite; this book and the release pages practice it visibly. Kills: the document that is always right in hindsight. (Chapters ten, eleven, and the release history.)

One more honest sentence, because the laws demand it of the page that states them: the mechanical half of laws two and three is enforced on Claude Code; on every other tool these laws travel as written instruction, which is the discipline shape, not the machinery shape, and chapter ten is the honest map of that difference.

Chapter oneMonday, and what actually goes wrong

Forget the product for a moment. Here is a Monday.

You run a small tea company. The order totals are wrong by a penny sometimes, and a customer noticed. You open your AI coding assistant and say: add VAT to the order total, and please do not break the rounding again, we refunded someone last month over this.

It does a good job. It writes the code, it explains the fix, you ship it. Good Monday.

Now here is what happens over the next three weeks, and every item in this list is a mechanical property of how these tools work, not a complaint about how clever they are.

Tuesday: the sentence is gone

You open a fresh conversation, because the old one got long and slow. You ask for a discount feature. The assistant writes price * 0.9 using decimal numbers, because the sentence we refunded someone last month over rounding was in a conversation that no longer exists. You say it again. It apologises sincerely. It will not remember on Wednesday either.

That is not forgetfulness in the human sense. The assistant has no place to put that sentence. The conversation IS the memory, and the conversation ends.

Wednesday: two of them, one file

You get ambitious and run two assistants at once, one on VAT and one on discounts. Both decide the cleanest place to work is pricing.py. The second one saves over the first one's work. Nothing errors. You find out on Thursday when a test you were sure passed does not.

Thursday: it says it is done

You ask whether the VAT work is finished. It says yes, and it means it. It has no way to distinguish I wrote code that should work from I ran the test and watched it pass, because both feel the same from the inside of a sentence. You run the test yourself. It fails.

Friday: nobody can review anything

Your one actual engineer, Priya, asks why order totals are now recomputed at read time instead of stored. The answer is in a transcript. The transcript is four thousand lines long, it is on your laptop, and it is not organised by decision. She shrugs and rewrites it her way, which is a fourth different behaviour for the same field.

Three weeks later: the handover

You hire someone. They ask what the project is, what state it is in, and what decisions were already made and why. You have a repository and a memory. That is the whole handover pack.

What all five of those have in common

None of them is about the model being stupid. Every one of them is about something that was never written down anywhere a machine could check it.

What BrotherMode actually is

It is a small pile of Python scripts and one database file that sits in your project folder. It does five things, and each one is the direct answer to a day above.

The dayWhat BrotherMode does instead
Tuesday: the rule is goneYour correction becomes a stored rule with an approval receipt. Before work starts, matching rules are looked up and the lookup is recorded.
Wednesday: two writersOne writer per file, enforced by a program that runs before every edit and refuses the second one.
Thursday: unproven "done"Work cannot be marked complete without evidence. The command refuses.
Friday: unreviewable decisionOne command writes a review pack with the live code, the callers, the tests, the rollback and a place for Priya's verdict. Her critical objection can refuse the decision outright.
The handoverOne command writes a Documentation/ folder, including a handover page written for a human who will never talk to an assistant.

Two properties are worth naming now, because they explain most of the design decisions you will meet later.

The programs, not the model, write the record. When a session ends, a hook (a small program the tool runs automatically at a fixed moment) writes what happened. The model does not get to narrate its own numbers. This is why the numbers can be trusted, and it is also why there are no numbers in this book: the honest ledger for real use is currently empty.

Refusal over guessing. Almost everything in this system prefers to stop and print a reason. You will see the word refused more in this book than the word ok. That is deliberate. A tool that guesses when it is unsure produces work you then have to audit; a tool that refuses produces one line you have to read.

Before you go further. BrotherMode is a release candidate. Its own limits page opens with the sentence "Everything here rests on tests, adversarial execution, and simulated lifecycles. No day of real founder work has yet been done through the V2 store." Its continuous integration has failed on Windows. If you want a finished product with case studies, this is not it. If you want a system whose honesty you can check, read on.

Try this now

No install needed, and nothing here writes to your project. Open a terminal in any project you have and ask git the question the handover chapter will ask later:

git log --oneline -20

Now try to answer, from that output alone: which of those commits was a decision somebody made on purpose, and what was the reason? You will not be able to. That gap, between what the repository records and what you actually need to hand over, is the gap this book is about.

Chapter twoInstall it in ten minutes

Three paths now, and this section was rewritten on 2026-08-01 because the easiest one did not exist when this book was first written. The plugin path is two lines typed inside Claude Code. The pinned clone is the most-proven path and what the rest of this chapter walks. The team path adds one decision about where the shared memory lives.

The plugin path, two lines

/plugin marketplace add khalilmaaouni/BrotherModeUp
/plugin install brotherme

Typed inside Claude Code, one at a time. Restart if it tells you to, then type /brotherme-help to confirm. That install brings the seven guided commands of chapter thirteen, the guided skill, and the automatic hooks, with no cloning and no file editing. Honest label, in the same register as everything else here: this path has been through its full cycle exactly once, on the author's machine, from a local copy of the repository. If it misbehaves for you, the repository's issue page wants to hear about it, and the clone path below is the fallback that has been proven far more times. Do not run both paths on one machine: they wire the same hooks, and a machine carrying both runs everything twice.

What you need first

  • Python 3.9 or newer. Nothing else. No packages to install, no account, no network calls at runtime.
  • Claude Code, if you want the automatic parts. Everything else works from a plain shell in any tool. Chapter ten is honest about which is which.

Step 1: get the files

git clone --branch TAG --depth 1 \
  https://github.com/khalilmaaouni/BrotherModeUp.git \
  ~/.claude/skills/brothermode

Replace TAG with the current release tag, which you read from the repository's README rather than from this book, because the book would rot and the README is tested against the release facts on every run. When this chapter was rewritten the tag was v2.0.0-rc.11. Pinning a tag instead of cloning a moving branch matters here more than in most projects: this code runs automatically on every future session through hooks, and code that auto-runs should come from a fixed, checkable snapshot. The path is the installation: Claude Code looks for skills under ~/.claude/skills/, and the scripts work out their own location from there.

Step 2: prove it works on your machine before you wire it in

cd ~/.claude/skills/brothermode
python3 tools/test_all.py

This runs every test suite, one at a time in its own process. It takes a minute or two. That is the cost of the isolation, not a hang. You are looking for one thing only, the last line: ALL GREEN. A skip or two is normal and is reported as a skip.

Do not memorise a test count. Counts change every time a test lands, and a book that pinned one would teach you to distrust the book instead of the tree.

Step 4: prove the fence is live, not just wired

This is the step people skip and should not. Wired and working are different things.

python3 ~/.claude/skills/brothermode/scripts/doctor.py

What it printed:

BrotherMode doctor: fence hook
  settings: /tmp/bmbook/fakehome/.claude/settings.json
  note: fence command: python3 .../tools/bm_fence_hook.py
  OK: for each of Edit, Write, MultiEdit, NotebookEdit, the wired hook denied a
      foreign write and allowed the owner's own write, in a throwaway project
      that has been deleted.

What this does NOT prove, stated so it is not assumed:
  - The fence FAILS OPEN by design. A missing store, a corrupt store, a store with
    no active claims, or any bug in the hook allows the write and prints a line
    starting 'bm_fence_hook: FAILING OPEN'. A hook that fails closed would brick
    editing, which is a worse failure than an unenforced fence, so this is a choice
    and not an oversight.
  - Bash is NOT gated. Shell redirection, sed -i, tee, python -c and the rest write
    files without passing any hook.
  - Claude Code loads settings at session start, so a settings file corrected during
    a session is live at the NEXT session, not this one.

Read the second half twice. Doctor built a throwaway project, claimed a file under one session, asked the hook you actually wired to approve an edit from a different session, watched it refuse, then asked again as the owner and watched it allow. Then it told you three things it did not prove. That paragraph is the most useful output in the whole install, and most tools would not print it.

The Bash hole is real and is policy, not a bug. The fence stands in front of the structured edit tools. It does not stand in front of sed -i, tee, a shell redirect, or python -c. If your team treats "run a shell command that rewrites the file" as normal, the fence will not save you. Chapter eight tells you how to work with that instead of pretending it away.

Step 5: point the memory somewhere

The vault is a plain folder of markdown and text files: session logs, the machine-written ledger, and optionally a model of how you like to work. Nothing in it talks to a server.

cp -R ~/.claude/skills/brothermode/vault-template ~/BrotherModeVault
export BROTHERMODE_VAULT="$HOME/BrotherModeVault"

Put that export line in your shell profile so it survives a restart.

Step 6: restart, then check

Hook configuration is read when the tool starts, so a session already running does not have your new hooks. Restart, then:

python3 ~/.claude/skills/brothermode/tools/bm_score.py

On a fresh install most checks say NO-DATA. That is the correct answer, not a failure. You have no history, and this tool refuses to invent one. A check without data says NO-DATA, never PASS.

The team path: two extra decisions

Where the project store lives. Each project gets a .brothermode/ folder holding a small database. It is per project, not per person, and it lives next to the code. The usual choice for a team is to keep it out of git (add /.brothermode to .git/info/exclude) and let each person have their own, using the store for coordination inside one machine and the generated Documentation/ folder, which IS committed, for coordination between people. Chapter eight walks through why.

Whose vault is whose. The vault holds your session logs and notes. Give each person their own. It is a folder; there is nothing clever to configure.

Chapter threeYour first loop

A loop is one unit of work with a beginning, a middle and a provable end. That is the whole idea. It is called a loop rather than a task because the end feeds back: the evidence you produce at the end is what the next loop reads at its beginning.

Four commands. Everything below was run in a throwaway project called tealeaf: a git repository with one module, src/pricing.py, and one test.

Command 1: claim the work and the files

Two ideas in one command. You are naming a unit of work, and you are declaring which files it is allowed to write. That second half is the fence.

python3 tools/bm_store.py claim vat-rounding \
  --lifetime persistent \
  --objective "Add VAT to the order total without floating point rounding drift" \
  --files src/pricing.py \
  --session "$ME" \
  --tier T1 \
  --check "python3 -m unittest discover -s tests -q"
claimed 'vat-rounding' as lifecycle f1a2f8b449194dd2bf608831cd440a1d
  (version 1, session bm1-c03e7b279b1cfe4b835074f8)

Three of those flags deserve a sentence each.

--check
The command that will prove the work. You write it before you do the work, when you still have to think about what proof would look like. Afterwards you will accept anything.
--session
Who holds the fence. This is not your name; it is a label for one working session, produced by a helper (see the box below).
--tier
How much effort you are budgeting: T1 for a single focused session, T2 for a few parallel helpers, T3 for a fleet with divided scopes. It exists so that spend can be judged against a declared intent instead of a feeling.

The long hex string is a lifecycle: a permanent identity for this unit of work that nothing else will ever reuse. And version 1 matters more than it looks. Every later command must tell the store which version it last saw. If the record moved in between, the command refuses instead of overwriting. You will see that refusal in chapter eleven, and you will be glad of it.

Where $ME comes from. Do not invent a session label. Ask for it:

ME=$(python3 tools/bm_fence_hook.py session-label --session-id sess-mon-morning)
echo $ME
bm1-c03e7b279b1cfe4b835074f8

The label is derived from a secret token stored inside your project, so it is stable for that session and cannot be forged by another one. A label you typed by hand would mint a token nobody else can reproduce, and would quietly lock you out of your own records. Your labels will not match the ones printed in this book; that is correct.

Command 2: record the decision, not just the code

When you make a choice that a future person would ask about, spend one line on it.

python3 tools/bm_store.py decide f1a2f8b4... --version 1 \
  --topic "money representation" \
  --text "Keep every amount in integer pence and round VAT half-up at the order level, not per line."
decision 1 recorded for f1a2f8b449194dd2bf608831cd440a1d (version 2)

Note that it hands you back the new version number. That is a small kindness with a history: an earlier version bumped the version silently, so your very next command failed against a number you had never been told.

Command 3: checkpoint, before you might die

A checkpoint says where you got to and what comes next. Write it before anything risky, not after.

python3 tools/bm_store.py checkpoint f1a2f8b4... --version 2 \
  --next "write the failing test for a 5 percent VAT on 900 pence" \
  --blockers "none"
checkpoint 1 recorded for f1a2f8b449194dd2bf608831cd440a1d (version 3)

This is the same instinct a database has when it writes its log before its data. If the session dies now, what survives is not just the files but the next step, which is the part that actually hurts to lose.

Command 4: complete, and try to cheat

Here is the interesting one. Try to close the work without proof:

python3 tools/bm_store.py complete f1a2f8b4... --version 3
refused (missing-evidence): active -> complete requires non-empty evidence
  (the check_cmd result)

There is no flag to skip that. So run the check you declared at claim time:

python3 -m unittest discover -s tests -q
Ran 1 test in 0.000s

OK

Then close it, pasting what you actually saw:

python3 tools/bm_store.py complete f1a2f8b4... --version 3 \
  --session "$ME" \
  --evidence "python3 -m unittest discover -s tests -q => Ran 1 test, OK"
complete: 'vat-rounding' (lifecycle f1a2f8b4...) is now complete at version 4

Nothing stops you writing a lie in that string. But a lie now has to be typed deliberately, into a field whose only purpose is proof, and it will sit in the generated handover document under the heading "the command that proves it". That is a very different act from saying "done" in a chat.

Chapter fourThe five questions, kept apart

Most tools that claim to learn from you collapse five different questions into one. Then you cannot tell a good idea from a bad habit, because the record of both looks the same.

Here they are, separated:

Why the separation earns its keep

Suppose a rule turns out to be wrong. With the five kept apart you can ask which one broke:

  • Capture was wrong: you never said that. The raw text settles it.
  • Interpretation was wrong: you said it, but the rule written down means something wider than you meant.
  • Approval was wrong: the rule was right for that moment and should not have been made standing.
  • Application was wrong: the rule is fine, it was retrieved for work it does not apply to.
  • Outcome was wrong: everything worked as designed and the rule is simply a bad rule.

Those are five different fixes. A single "learned preferences" list cannot tell you which one you have.

Stage 1 and 2: capture

Capturing is one command, and it changes nothing:

python3 tools/bm_learn.py capture \
  --trigger "when I touch money in this project" \
  --action "keep every amount in integer pence and never use a float" \
  --because "a float rounded a customer invoice wrong last month" \
  --scope project
captured fd93a141 (pending, nothing changes until you approve it)
  heads up, this looks like more than one rule: contains 'and never', which
  usually joins two rules
  approval will refuse it unless you split it or pass --override-reason

It caught something real. "Keep amounts in pence" and "never use a float" are two rules, and a rule that is secretly two rules cannot be graded, because you never know which half was followed. Split it:

python3 tools/bm_learn.py capture \
  --trigger "when I touch money in this project" \
  --action "keep every amount in integer pence" \
  --because "a float rounded a customer invoice wrong last month" \
  --scope project
captured 9b832875 (pending, nothing changes until you approve it)

--scope is how wide the rule reaches: global, project, domain, artifact, relationship or tool. A preference about this codebase is not a law about all your work, and the scope is where you say so.

Stage 3: approval, in two halves

This is the part of the design worth understanding, because it is unusual. Approving a rule takes two commands, not one.

python3 tools/bm_learn.py grant-approval 9b832875 \
  --answer "yes, integer pence everywhere, that bug cost us a refund"
approval receipt b4440dc0 for candidate 9b832875
  expires 2026-07-30T02:05:50Z (900 seconds), one candidate, one use
  it dies if the candidate or the rule text changes before you approve

  RECEIPT TOKEN, shown once and stored nowhere:
  a913dee38dd443a97726095e1c92875492d9f400263dc1ac

  spend it: bm_learn.py approve 9b832875 --receipt <token>
  or put it in BM_APPROVAL_RECEIPT so it stays out of your shell history
  do not paste it into a log, a transcript or a commit message
python3 tools/bm_learn.py approve 9b832875 \
  --receipt a913dee38dd443a97726095e1c92875492d9f400263dc1ac \
  --ref "founder said yes in the Monday session; the refund is in the ledger"
approved as rule 4873a92d
  4873a92d  [project:tealeaf, approved] v1
     When: when I touch money in this project
     Do  : keep every amount in integer pence

Why the token? Because before it existed, any process that could run the tool could manufacture an approved rule, and the reference it recorded said "run by the founder" whether or not anyone was there. The token is minted only when someone records what the human actually answered, it is bound to that exact rule text, it expires in fifteen minutes, and it works once. Change a word of the rule after the question was asked and the token dies. There is no override and no break-glass.

Try to spend it twice:

refused (not-pending): candidate 9b832875 is 'approved', only a pending candidate
  can be approved

What the receipt does not claim. It does not prove which human answered. It proves an answer was given about this exact thing and has not been spent. No wording anywhere in the product says otherwise, and that restraint is the reason the mechanism is worth anything.

Stage 4: application, and the honest surprise

Before substantial work, ask what rules apply. This both retrieves and records the retrieval:

python3 tools/bm_learn.py apply \
  --query "add VAT to the order total" --session sess-mon-morning
no founder rules apply here (0 in scope, none matched; mode=lexical)
Gates: 0 of 0 applicable returned. A result limit cannot hide one.
Soft rules: 0 shown, none omitted.

Nothing matched, and that is the truth rather than a bug. The default matching is lexical: it compares the words in your query against the words in the rule. The rule says "when I touch money"; the query said "VAT" and "order total". No shared word, no match. Say it in words that overlap:

python3 tools/bm_learn.py apply \
  --query "change how money is added up in the order total" --session sess-mon-morning
RELEVANT FOUNDER RULES (mode=lexical)

  4873a92d  rank=1
  Scope: project:tealeaf     State: approved
  When : when I touch money in this project
  Do   : keep every amount in integer pence
  Why  : a float rounded a customer invoice wrong last month
  Match: terms ['money'], relevance 0.143

recorded 1 application(s), 0 already recorded for this task
  retrieval run e63adbfb recorded (1 eligible, 1 returned, limit 5)

Two practical lessons, and this is the sort of thing a marketing page would hide. First, write triggers in the words you will actually use: say "money" and "rounding" and "price", not a formal category name. Chapter fiveHow to correct it, and where the correction goes

You will correct it constantly. That is normal and is the input the whole system runs on. What matters is that a correction has somewhere to go.

The three lifetimes of a correction

When you say "no, not like that", you mean one of three things, and it helps to know which:

You meanLifetimeWhat to do
fix this one thing, here, nowthis sessionnothing. Just say it. Do not capture it.
from now on, in this projectstanding, project scopecapture, approve with scope project
from now on, in all my workstanding, globalcapture, approve with scope global, and think twice

The most common mistake is turning row one into row three. A one-off frustration promoted to a global law will fire on unrelated work for months.

What happens to a correction, mechanically

Two paths in. The first you saw in chapter four: you capture it deliberately.

The second is automatic, and it is worth understanding because it is deliberately weak. At the end of a session, a hook scans your short messages against a pattern of correction-shaped phrases ("no, that", "i said", "from now on", "never do") and appends up to five candidates per session to a file. They are candidates, not verdicts. A regular expression cannot tell a correction from a quotation, so nothing is imported until you say so:

python3 tools/bm_learn.py inbox

That prints the queue and ends with a line that tells you nothing has been approved and how to import them. Nothing in that path can create a rule, because the receipt in chapter four stands in the way.

Rules are versioned, not overwritten

A rule you change keeps its history. Ask a rule to explain itself:

python3 tools/bm_learn.py why 4873a92d
rule 4873a92d4a2a4ee6b1d4726b8d2e272e
  4873a92d  [project:tealeaf, approved] v1
  When: when I touch money in this project
  Do  : keep every amount in integer pence
  Why : a float rounded a customer invoice wrong last month

  versions:
    v1  created  founder approval (receipt b4440dc0): founder said yes in the
        Monday session;...
  evidence (1):
    support founder_approval  receipt b4440dc0: founder said yes in the Monday
        session; the refun...

That is the audit trail: version, who approved it, which receipt, and the reason recorded at the time. Three verbs move a rule without destroying it:

deprecate
stop retrieving it, keep the history. The usual choice.
supersede
this newer rule replaces that older one, and the link between them is recorded.
reject
for a candidate that never became a rule. The reason is kept, so the same suggestion does not keep coming back.

Rejecting is not deleting, and the difference shows up immediately:

python3 tools/bm_learn.py reject fd93a141 --because "it joined two rules into one"
rejected fd93a141. The reason is kept, so the same suggestion does not keep
  coming back.

There is a forget verb for genuinely removing a rule from future retrieval, and it makes you say so twice:

forget removes a rule from every future retrieval. Re-run with --yes if that is
  what you want.

When a correction contradicts one you already approved

Rules that fight each other are the failure mode of every "learned preferences" system, because the newest one silently wins and you never find out. There are two commands for this, conflicts to list them and resolve-conflict to settle one, and the resolution is recorded rather than inferred from timestamps.

Grading a rule that hurt you

The last verb closes the loop back to chapter four's fifth question. If work went wrong because a rule was followed, say so:

  --note "what happened"

The two kinds are rework (it had to be redone) and escaped_defect (it shipped and was wrong). This is the only input that can make a rule look bad in the record, which is exactly why it needs to be easy to type on a bad afternoon.

Chapter sixGates and deep dives: reviewing a machine's decision

A gate is a moment where a decision needs a human before it becomes standing behaviour. Chapter four's approval receipt is the mechanism. This chapter is about the harder half: giving the human enough to decide with.

Asking Priya "should we recompute totals in a migration or at read time?" in a chat message is not a review. She needs the code, the callers, the tests, the blast radius and the way back. That is what a deep dive pack is.

Nothing is generated until you ask

Packs cost time to produce and go stale if nobody reads them, so none exists until someone asks for one. First, the cheap question: what are the stakes, and where would the pack live?

An alert guards the gates it is anchored to, which is narrower than every gate, and you should know the difference before you rely on it. The refusal fires when the unresolved critical alert is anchored to that candidate, to the work record the candidate came from, or to any file in the change set the approval would touch. The objection does not chase the wording around.   front of this approval: Priya wrote 'no dry run mode on anything that rewrites
  this file' about file src/pricing.py (note c82261b2). Resolve it, or re-run with

Three limits of the fence, stated plainly.

It fails open. A missing store, a corrupt store, a store with no active claims, or a bug in the hook allows the write and prints a line beginning bm_fence_hook: FAILING OPEN. The author reproduced this by adopting a record without re-claiming its paths: the store then had no active claims and the very next edit was allowed with that exact warning. Failing closed would brick editing, which is worse, so it is a choice; but it means you have to read the warning.

Bash is not gated. sed -i, a shell redirect, tee, python -c: all of these write files without passing any hook. This is policy, published in the project's own documentation.

Adopting is not claiming. Taking a record over transfers the record, not the fence. Re-claim the paths afterwards or you are working unfenced. The refusal message tells you this, in its last line, and it is easy to skim past.

Now the fence has flipped. Priya's write is allowed and the previous owner's is refused, and neither of them had to remember anything:

The one wrinkle worth knowing. --handover is real and it works, and it is not listed in the park usage line. Run park with no arguments and you get usage: park <lifecycle_uuid> --version N [--session SID] [--note TEXT], with no mention of it. Type it anyway. A --note is a note to yourself; a --handover is a document for the next person, and only the second one shows up in handovers and in STATE.md.

Problem three: the same person, a new machine or a dead session

This is the same mechanism with a different motive, plus two hooks. Before a compaction (the moment your tool discards old context to make room, which is exactly when work goes missing), a hook snapshots your entire working tree, untracked files included, into a private git reference. It never touches your branch, your index or your working tree, and it never pushes anywhere.

Recovering does not overwrite anything either:

python3 tools/bm_autosave.py recover
bm_autosave: recovered snapshot 81aa7526... into a NEW worktree at:
  /var/folders/.../bm-autosave-recover-7ay6aggs
  permissions: 0700 (owner-only; best-effort only on platforms, e.g. Windows,
  that do not fully enforce a POSIX mode)
  Your live working tree at /private/tmp/bmbook/tealeaf was never touched. Inspect
  the folder above, copy back what you need, then run
  `git -C ... worktree remove ...` when you are done with it.

And it warns you about what it captured, which matters if a team member has secrets sitting untracked:

bm_autosave: WARNING: this snapshot captures 20 untracked file(s) that no commit
  has ever reviewed: Documentation/00-START-HERE.md, ... Anything secret in that
  list belongs in .gitignore or in BROTHERMODE_AUTOSAVE_EXCLUDE.

The owner-only guarantee is POSIX only. The recovered folder is readable only by you because of a file mode of 0700. Windows governs access differently and the project's own limits page records this failing on both Windows legs of its continuous integration. On Windows, treat a recovered worktree as readable by anyone with an account on the machine.

Problem four: another team, another repository

Here is the honest answer: this is coordinated, not enforced. A store is per repository. Two repositories are two stores that know nothing about each other, and the author verified exactly that. In a second repository, the payments team claimed their own file:

claimed 'charge-idempotency' as lifecycle 8e52ad87bd864e91a8329c2e06f29987
  (version 1, session bm1-5008d7e9bf0215ae3a25c3a1)

From the tea repository, that record is invisible. Counting mentions of it in the tea project's own dashboard returns zero. There is no cross-repository lock and the book will not pretend there is one.

What does work, and works well enough to plan against, is that each repository generates a plain text description of its own state that the other team can read:

grep -A3 "^## active" ../payments/STATE.md
## active
- charge-idempotency (8e52ad87bd864e91a8329c2e06f29987, version 1, persistent) [T2]
  owner-session: bm1-5008d7e9bf0215ae3a25c3a1
  objective: make charge idempotent before tealeaf starts sending VAT totals
  files: api/charge.py

That is a working cross-team protocol, and it needs no new software:

  1. Each repository commits its Documentation/ folder. The store is local; the generated folder is the shared artefact. That is why regeneration being byte-identical (chapter seven) matters: a document that churns is a document nobody reviews.
  2. Depend on the other team's decision index, not their chat. Documentation/30-decisions/INDEX.md is the contract surface: every decision, its state, and the pack that reviews it.
  3. File your objection in their repository, anchored. A note of kind alert at severity critical in their store refuses their gate. It is the one cross-team mechanism with real teeth, and it works because you are writing in the repository whose gate you want to stop.
  4. Write the dependency into the objective. The payments objective above literally says "before tealeaf starts sending VAT totals". Not elegant. Readable by everyone, at the top of a committed file, forever.

A tool you might reach for and should not trust here. bm_telemetry.py fence-lint is documented as printing the live fences from a project's STATE.md plus any repositories you point it at through the BROTHERMODE_REGISTRIES variable, which sounds exactly like cross-repository fence awareness. The author ran it against two repositories with two active fences and got:

fence-lint: no live fences found under /private/tmp/bmbook/tealeaf

The reason is a format mismatch: it matches an older hand-written fence line format, and the store-generated STATE.md does not use it. Use the grep above instead. This is reported to the project rather than papered over here.

A team convention that costs nothing and saves afternoons

Claim narrowly and claim late. A fence over src/ blocks four people; a fence over src/vat.py blocks nobody. If you genuinely need a wide fence, use --lifetime ephemeral so it is understood to be short, and remember that a fence past its stated lifetime is treated as released rather than blocking the team forever.

So the practical shape of using another tool is this. Everything you do by typing a command works. The store, the fence claims and their refusals, the rules, the packs, the documentation folder: all of it is an ordinary local program reading standard input and writing standard output. It needs no verification per runtime, and the project says so.

Everything automatic is Claude Code only, today. The five hooks parse Claude Code's payload format. Nobody has captured a real payload from any other runtime, which is why every non-Claude answer in that column says UNVERIFIED rather than "probably fine". Qwen Code names SessionStart and SessionEnd, the two events the telemetry actually targets, which makes it the most promising target and still not a verified one.

Why the distinction is a safety matter, not pedantry

Consider wiring the fence hook into a runtime whose payload does not carry a session identifier where BrotherMode expects one. The hook cannot tell who is writing, so it fails open, and failing open is silent by design. You would have a project with a PreToolUse entry in its configuration, a team who believe one writer per file is enforced, and no enforcement whatsoever. That is strictly worse than knowing you have no fence, because a team that knows will be careful.

Two further honest notes the project makes about itself. In a runtime with no hook points, the fence is advisory: BrotherMode can tell the tool the law and the tool can run the store commands, but no gate stands in front of a write, so one writer per file is a coordination ledger rather than a boundary. And there is no automatic installation of adapter files, because AGENTS.md at a repository root usually already has content in it, and a generator that overwrote it would be a data loss bug wearing a convenience feature's clothes.

Chapter elevenWhen it goes wrong

Sorted by how likely you are to hit it. Every message quoted here was produced by the author on purpose.

"refused (stale-identity)"

refused (stale-identity): expected version 3 in a state that allows -> active;
  found version 3 state 'adopted'

What happened. Every mutating command takes --version N, the version you last saw. If the record has moved since, the command refuses rather than overwriting whatever happened in between. In the case above, the version was right but the state was wrong: the record had been adopted, and adopted does not move straight back to active.

What to do. Look at the record, then use what you see:

python3 tools/bm_store.py dashboard

This is not an error to work around. It is the thing standing between you and a lost afternoon on Wednesday.

"FAILING OPEN, the write is allowed and the fence was NOT checked"

bm_fence_hook: FAILING OPEN, the write is allowed and the fence was NOT checked.
  Reason: the store at .../.brothermode/store.sqlite3 holds no active claims, so
  there is no fence to enforce

What happened. The most common cause is the one the author hit while writing chapter eight: a record was adopted but its paths were never re-claimed, so no active claim existed and there was nothing to enforce.

What to do. Re-claim the paths, then confirm they are there:

python3 tools/bm_store.py claim <name> --files <paths> --session "$ME"
python3 tools/bm_store.py dashboard

Never treat this line as noise. It is the exact wording that separates "the fence allowed it" from "there was no fence".

The rule you approved never fires

What happened. Almost always word overlap. Matching is lexical by default, as chapter four showed: a rule triggered on "money" does not match a query about "VAT".

What to do. Run the retrieval and read the diagnostics it prints for free, including the mode and the matched terms:

python3 tools/bm_learn.py lookup --query "<the words you would really use>"

lookup reads and records nothing, so it is the safe verb for debugging. Then rewrite the trigger in the vocabulary you actually type. There is an optional stemmed index behind BROTHERMODE_FTS5=1, and index-status reports whether it is really answering, but fixing the words is usually the better fix.

The hooks are wired and nothing happens

Three causes, in order of likelihood. The settings file is not valid JSON, in which case the whole hooks block is ignored and nothing says so. Or the tool has not restarted, and hook configuration is read at startup. Or the session was too short: the telemetry has a deliberate activity floor and does not record a trivial session, so the ledger cannot be padded.

python3 -m json.tool ~/.claude/settings.json
python3 ~/.claude/skills/brothermode/scripts/doctor.py

A pack refuses to regenerate

  anchor but their content changed since this pack was written. Read the new text
  and re-cite with --recite src/pricing.py:7-12@return unit_pence * quantity to
  record that you did.

Working as designed. Read the new code, then pass the --recite argument it handed you. Note what that does: it records that a human looked. Passing --cite again will not clear it, and that is deliberate.

Health check, when something feels off but nothing has errored

python3 tools/bm_store.py verify
verify: healthy, 0 problem(s)

python3 tools/bm_autosave.py recover

If nothing was ever saved it says exactly that, rather than pretending:

  is empty and no snapshot ref is newer than the last clean check).
  No snapshot refs exist for this worktree at all.

Two things that will annoy you and are not broken

A pile of STATE.md.bak-... files. Every render backs up the previous file first. The author's throwaway project accumulated seven of them in about fifteen minutes of normal use. They are safe to delete and the tool will not delete them for you, because a tool that decides on its own which of your files are disposable is a tool you cannot leave alone with a project. Add STATE.md.bak-* to your .gitignore.

--help is not always --help. Several commands print their usage only when you give them no arguments at all, and treat a flag as data otherwise. Running bm_store.py claim --help creates a work record actually named --help, which the author did while researching this book and had to clean up. Run the bare verb (bm_store.py claim) to see usage. For the learning tool, an unrecognised flag is properly refused and it lists the flags it does know, which is the behaviour you want:

bm_learn: unrecognized flag --query (recognized: --architecture, --communication,
  --json, --multi-file, --prior-correction, --risky)

The limits worth knowing before you rely on this

Chapter twelveGlossary

Part two's four additions first (added at 2.0.0-rc.11), then part one's entries, alphabetical. Every entry describes what the thing is, not what it might become; part one's entries are as of commit 471efdc.

deep tour
The generated where-does-my-project-stand page behind /brotherme-help: state, diagrams, data model, decisions, code map, and a co-build section for developers. Chapter thirteen. Sections whose source folders do not exist yet say "not yet recorded" instead of inventing content.
guided layer
The seven /brotherme commands and the conductor behind them: the plain-words surface over the machinery in part one. Chapter thirteen.
guided loop
The routing law for delegated work: the strongest model plans and judges, cheaper helpers execute, and a helper that fails its check twice is replaced by a stronger one. Written law in the delegation reference, pinned by tests.
marketplace (plugin)
The repository doubles as a Claude Code plugin source: add it once, install brotherme from it, and the guided layer registers on next start. Chapter two, the plugin path.
agent
A model working on a task with tools, in its own conversation. When you ask an assistant to spawn helpers, each helper is an agent. In BrotherMode each one is expected to hold a fence and to declare a tier, so its spend can be judged against a declared intent.
alert
A kind of note carrying a severity. An unresolved alert at severity critical, anchored to a decision or to a file that decision would change, refuses the approval. Chapter six shows the refusal.
anchor
Where a note is attached: a file and optionally a line, a decision, a gate, or a work record. Notes render at their anchors in the generated pages. A note whose anchored line has moved is reported rather than silently dropped.
candidate
A captured correction that has not been approved. Completely inert: it changes nothing at all until a human approves it, and it can be rejected with a reason so the same suggestion stops coming back.
change set
The files an approval would affect, discovered from the store rather than asserted: the claimed paths of the work record the correction came from, plus the scope key when the scope is a single file.
check
The command that proves a piece of work. Declared at claim time with --check, before you know how the work will go, because afterwards you will accept anything as proof.
claim
Registering a unit of work and the exact set of files it may write. The second half is the fence.
compaction
The moment your tool discards older conversation to make room for new. Useful and necessary, and the moment work most often disappears, which is why a hook snapshots your files and your next intent just before it happens.
deep dive pack
A generated markdown document for one decision, in eight fixed sections, complete enough for an engineer to review the choice without reading a transcript. Generated on demand and never before.
evidence
The pasted result of running the check. Required, in a non-empty form, to move work to complete. There is no flag to skip it.
fail open
When something goes wrong, allow the action rather than block it. The fence hook fails open on purpose: a broken hook that blocked every edit would be worse than an unenforced fence. It always says so out loud, and that line is the one you must never ignore.
fence
The set of files one worker may write. Enforced twice: the store refuses an overlapping claim, and a hook refuses the actual edit. It does not cover writes made through shell commands.
gate
A moment where a decision needs a human before becoming standing behaviour. Also used for a check severe enough to block work landing, as opposed to a soft check that is only scored.
handover
Two related things. A heading written when work is parked, stored in the same transaction so the explanation cannot be lost, and listed until someone acknowledges it. And a generated page, 40-handover/HANDOVER.md, written for a human who will never talk to an assistant.
hook
A small program your tool runs automatically at a fixed moment: session start, session end, before an edit, before a compaction. The point is that it does not depend on the model remembering. BrotherMode wires five. Verified in Claude Code only, per chapter ten.
human block
Text between a pair of markers in a generated file. Preserved byte for byte through every regeneration, including through a refused one. It is the mechanism that makes a generated document safe to write in.
lifecycle
The permanent identity of one unit of work, a long hex string that nothing else ever reuses. Two things that look like the same task are two lifecycles.
loop
One unit of work with a beginning, a middle and a provable end. Called a loop because the evidence closing one is what the next one reads.
note
An authored row attached to an anchor, of kind insight, alert, question, review, todo or risk, carrying who wrote it and when. Resolved notes stay, marked resolved. No generator deletes one.
park
Putting work down without finishing it. With --handover it also writes the document for whoever picks it up.
receipt
A single-use, fifteen-minute token minted when someone records what a human actually answered about a specific rule. No receipt, no rule. It dies if the rule text changes, and there is no override. It proves an answer was given about this exact thing; it does not prove who gave it, and nothing in the product claims otherwise.
rule
An approved standing preference with a trigger, an action, a reason and a scope. Versioned, explainable through why, and retrievable. Retired by deprecating or superseding it, never by erasing its history.
scope
How wide a rule reaches: global, project, domain, artifact, relationship or tool. The most common mistake in the whole system is making a project preference global.
session label
The public name for one working session, derived from a secret token stored in your project. Get it from bm_fence_hook.py session-label; never type one by hand, because an invented label mints a token nobody can reproduce and locks you out of your own records.
store
The one database file, per project, under .brothermode/. One program is the only writer of it. Everything else asks that program.
tier (documentation)
How deep the generated Documentation/ folder goes: 1 lean, 2 standard, 3 full. Chosen from measured signals, with the reason printed. Rises on its own, never falls on its own.
tier (effort)
How much work you are budgeting: T1 one session, T2 a few helpers, T3 a fleet with divided scopes. Declared on the claim so that spend is judged against an intent rather than a feeling.
unverified
Used in this project as a technical term, not a hedge. It means nobody has captured the evidence, so acting as though the capability exists would be guessing at a safety boundary. Every non-Claude entry in the hooks column of chapter ten is unverified, and unverified means do not wire it.
vault
A plain folder of markdown and text files holding your session logs, the machine-written ledger and optionally a model of how you like to work. One per person. Nothing in it talks to a server. Movable with the BROTHERMODE_VAULT variable.
version (of a record)
A counter every mutating command must state. If the record moved since you last looked, the command refuses instead of overwriting. This is the mechanism behind most of the refusals in this book, and it is the reason two workers cannot silently clobber each other's state.

Chapter thirteenThe guided layer: seven commands and the deep tour

Everything in part one you could drive from a shell. This chapter is the layer that means you never have to: seven slash commands inside Claude Code that wrap the whole machine in plain words. It arrived with 2.0.0-rc.10 and rc.11, after this book's first twelve chapters were written, which is why it gets its own chapter instead of being woven through them.

The design rule behind the layer, stated once so the rest of this chapter makes sense: the machinery never leaks upward. Underneath, the commands enter flows in a conductor file, which reads the same law files every expert session reads. On the surface, you type plain words and get plain words back: outcome first, one recommended next action, estimates as ranges. If you want the internals, you ask for the advanced view; you are never handed them by default.

The seven, and when to reach for each

  • /brotherme-start begins a project. It asks what you want to accomplish, asks only the questions whose answers change the scope, and ends in a one-page brief you approve before anything is built. That brief is the Project Canvas, saved as CANVAS.md at the top of your project folder; part one's chapter four is the law it follows.
  • /brotherme-status answers where things stand in exactly eight plain lines: goal, direction, progress, time remaining, decision needed, risk, evidence, next step. After a crash, a restart, or a week away, this is the command that reads the thread back.
  • /brotherme-next recommends exactly one next step, with a reason and a time range. If a decision of yours is what blocks progress, you get the decision card instead, recommended option first.
  • /brotherme-review checks work in progress against a written definition of done, point by point, pass or not-yet with evidence, and never softens a failing point.
  • /brotherme-deliver closes work out. It fills a delivery packet, and it refuses to call the work delivered without a check that ran after the last change and passed. No proof, no done, said plainly.
  • /brotherme-update reads your installed version, checks the newest release, and gives you the exact update lines for your install path. It says plainly when the network refused the check instead of guessing, and updating never touches your projects or records. Worth naming precisely: that version check is the one deliberate network reach in the whole product, made only when you ask for it; the hooks and tools that run on their own still make no network call, which is the posture SECURITY.md states.
  • /brotherme-help explains what you have in plain words, and offers the deep tour described next.

Chapter fourteenThe vault and Obsidian: how it remembers

Part one mentioned the vault whenever memory mattered and moved on. This chapter stays. If you use BrotherMode for more than one afternoon, the vault is the part you will end up caring about most, because it is the difference between a tool that starts over every morning and a colleague who remembers.

What the vault is, and why it is deliberately boring

The vault is a plain folder of markdown files on your own disk, default ~/BrotherModeVault, movable with the BROTHERMODE_VAULT environment variable. It holds the durable record: what each project is, what work is open, what decisions were made, and what mistakes already cost something once. A session reads it at the start of work and writes to it at milestones and at the end, so a crash, a restart, or a context compaction has something to recover from besides a model's fading memory of the conversation.

It is markdown on purpose, three reasons in order of how much ignoring them would hurt. It survives every tool change: if the editor, the AI tooling, or Obsidian itself disappeared tomorrow, every note still opens anywhere. It diffs and greps like code, so the instincts you already have work on your own memory. And it stays legible to a tired human at two in the morning, which is exactly who reads it.

The folder map

  • Home.md is the front door: a project table and links out to everything below. Sessions update its lists at close.
  • AGENTS.md is the vault's constitution: what a session reads at start, when it checkpoints, what it writes at close, how linking and forgetting work. Read it once yourself; every session is bound by it.
  • 10-Projects/ holds one folder per project: an Overview, an Open-Items list (dated, newest first, closed the session they resolve), and a Sessions folder of dated logs. A session log is written at every close, so the next session, or the next person, starts from a page instead of a guess.
  • 40-Failures/ is the do-not-step-in-the-same-hole-twice folder: an index read before starting work in any area, one line per costly or repeatable mistake, each linking to the full note.
  • 50-Reference/ holds standing material that is neither a project nor a failure, including the append-only log of observed weaknesses that feeds the weekly review.
  • 90-Archive/ is deliberate forgetting: superseded notes move here, each leaving a one-line pointer at the old location so a stale link still says where the truth went. A vault that only grows becomes noise.
  • 99-System/telemetry/ is machine-written only. Hooks append outcome and correction records here; humans and sessions read them but never hand-edit them, the way you would not hand-edit a live log file.

The rhythm a session follows

At start: Home, the project's Overview and Open-Items, the Failures-Index, and the last session logs. At milestones (a plan approved, a build green, a fact confirmed): checkpoint findings into the vault immediately, not only at the end, because the session that waits for the end sometimes never reaches it. At close: one dated session log, Open-Items updated, qualifying failures recorded, Home refreshed. One more rule that matters in practice: a missing or broken vault is stated plainly and worked around, never a reason to stop. Memory problems never block work.

Obsidian: a nicer window, never a dependency

Obsidian is a free desktop and mobile app built around exactly this shape of data: a folder of linked markdown files it calls a vault. Install it from obsidian.md/download, choose "Open folder as vault", and point it at your vault folder. The bracketed [[wiki-links]] in every note become clickable, and the graph view draws how your projects, decisions, and failures connect, which is a genuinely useful way to see the shape of your own memory. Personal use is free by Obsidian's own pricing page; no plugin is needed.

And none of it is required. Outside Obsidian a wiki-link is plain readable text, every note opens in any editor, and nothing in the hooks or tools checks whether Obsidian exists. The vault is the memory; Obsidian is a window.

What this does for collaboration

The vault is also the quiet answer to "how do I bring someone in". A new person, or a fresh session on a new machine, reads Home, the project Overview, the Open-Items, and the last two session logs, and knows where things stand without a single handover call. Chapter nine's handover discipline and the deep tour from chapter thirteen both lean on this: the record is already written, because writing it was never optional.

One honesty note to close: you may see Mem0, a hosted semantic-memory service, mentioned in the design documents as a possible future. This project ships no Mem0 integration, on purpose: it would send your data to a third party's servers on every use, which conflicts with the posture stated in SECURITY.md (nothing that runs on its own makes a network call; the one deliberate exception is the user-invoked version check in chapter thirteen). The vault on your own disk is the memory.

Building the cleaned view

The fix is two operations: dedupe on order_id, and convert the legacy_uk rows out of the currency the column claims and into the currency the values actually are.

FX_GBP_USD = 1.27  # fixed rate for this walkthrough

seen = set()
cleaned = []
for r in rows:
    if r["order_id"] in seen:
        continue
    seen.add(r["order_id"])
    amount = float(r["amount"])
    if r["source_system"] == "legacy_uk":
        amount = round(amount * FX_GBP_USD, 2)
    cleaned.append({**r, "amount_usd": amount})

naive_june = sum(float(r["amount"]) for r in rows if r["period"] == "2026-06")
clean_june = sum(c["amount_usd"] for c in cleaned if c["period"] == "2026-06")
naive June revenue (no cleanup): $636.00
cleaned June revenue (deduped, fx-converted): $604.15

The naive and cleaned totals differ by $31.85, which looks small enough to shrug off, and that is the trap. Broken into its two causes it is not small at all: removing the two duplicate rows takes $71.00 out of the naive total, and converting the legacy_uk rows out of their mislabeled currency adds $39.15 back in, because 29 GBP is worth more than 29 USD, not less. The net gap is small only because the two errors partly cancel. A fix that caught just one of them, the more visible one, would still ship a wrong number with a deceptively small distance to the truth. Before this number goes anywhere, the law says it needs one independent derivation, not a re-read of the same code. Dana hand-checks a single row:

hand-check on order 1005 (customer C005, legacy_uk):
  stored amount=29.00 currency=USD (mislabelled, actually GBP 29.00)
  29.00 * 1.27 = 36.83
  cleaned pipeline produced amount_usd=36.83
  match: True

One row, worked by hand, on a calculator rather than in the pipeline's own code path. That is the cheapest form of second check there is. Honest scope on what it covered: the hand-check verifies the currency conversion half of the cleaning, and the dedupe half of $604.15 was not independently rechecked by it; a stricter second route would recompute the total without reusing the pipeline's dedupe. The number releases with that scope stated, not hidden.

The centerpiece: two routes to churn, and they do not agree

Revenue was the easy headline number, because a hand-check on one row is a real independent route. Churn is harder, because the dashboard's actual query does not touch revenue alone: it joins to a customers table to break the number out by segment, retail against wholesale. Route A is that real query, the one the dashboard will run every week from here on:

SELECT count(*) FROM (
  SELECT DISTINCT r.customer_id FROM revenue r
  WHERE r.period = '2026-06'
  AND r.customer_id NOT IN (
    SELECT customer_id FROM revenue WHERE period = '2026-07'
  )
) churned
JOIN customers c ON c.customer_id = churned.customer_id
churned customers (route A, joined to customers): 8
churn rate (route A): 8/12 = 66.7%

Note the grain mix already visible in that line, in the chapter about catching grain bugs: the 8 comes from fanned-out joined rows while the 12 in the denominator counted distinct customers and did not fan out, which is part of why the number is wrong and not merely inflated evenly.

Before that number goes in front of the board, the law requires a second, independent derivation, and the word independent is doing real work: it has to be a route that does not share the first route's joins, because a bug living in a shared join would pass a check that only re-reads the same join. So route B never touches customers at all. It works off revenue alone, as two plain sets:

june_active = {r["customer_id"] for r in rows if r["period"] == "2026-06"}
july_active = {r["customer_id"] for r in rows if r["period"] == "2026-07"}
churned_set = june_active - july_active
churned (route B, set difference): ['C004', 'C006', 'C007', 'C009', 'C011']
churned customers (route B): 5
churn rate (route B): 5/12 = 41.7%

DISAGREEMENT: route A says 8, route B says 5.
Do not ship either number. Find out why before anyone sees it.

Eight against five is not a rounding difference; it is a different fact about the business, and the law is explicit about what happens next: neither number ships until the disagreement is explained. This is the whole point of doing the second derivation before anyone sees the first one. A number shown first and checked only if someone happens to ask does not count as checked at all.

Dana goes looking for what route A's join could be doing that route B's set difference cannot:

duplicate customer_id rows: {'C001': 2, 'C004': 2, 'C007': 2, 'C011': 2}
cause: an address update re-inserted the customer instead of
updating the existing row, so the join fans out one-to-many

There it is: a join fan-out, the exact failure mode the project's data doctrine names by name. Four customers have two rows apiece in the customers table, because an address change wrote a new row instead of updating the old one. Three of those four (C004, C007, C011) are among the five customers who actually churned, so the join counts each of them twice, and route A's count(*) inflates 5 real churned customers into 8 counted rows. Fix the dimension, not the metric:

CREATE TABLE customers_dedup AS
SELECT customer_id, segment, updated_at FROM customers c1
WHERE updated_at = (
    SELECT max(updated_at) FROM customers c2
    WHERE c2.customer_id = c1.customer_id
)
customers rows before dedupe: 16
customers rows after dedupe: 12

route A, rerun against customers_dedup:
  churned customers (route A, fixed): 5
  route B (independent, unchanged): 5
  agreement: True

Now both routes land on five, forty one point seven percent, and the number is worth showing to a board precisely because it survived a route that could have disagreed with it and did not.

Where the guided loop sits in data work

None of the mechanical steps above needed a strong model. Reading a header, counting duplicates, writing the dedupe query, formatting the manifest as JSON: a cheap helper drafts every one of those, the same way chapter three's fast worker drafts a page layout. What a cheap helper does not get handed is the definition of churned, or which join is safe to trust, or whether an eight-versus-five disagreement is a rounding matter or a real bug. That judgment stays with Dana, the senior data engineer at the table, because it is exactly the kind of call a helper cannot verify against anything, only produce a confident guess about.

The refute posture from chapter six shows up here as the data reviewer: a checker whose only job is to try to break a headline number, the same way that chapter's gate let a critical objection refuse a decision outright. Route B was not a nice-to-have double check invented after the fact; a data reviewer's whole function is to plant a fan-out on purpose, or reach for a join-free route, and fail the number rather than the build. A number that only ever meets a checker built to confirm it was never really checked.

Try this now

Five minutes, stdlib only, no install. This is the same disagreement from the churn centerpiece, shrunk down to four rows and one duplicate:

import csv
import io

raw = """order_id,customer,amount
1,alice,10.00
2,bob,15.00
3,carol,20.00
4,dave,25.00
"""

def totals(text):
    rows = list(csv.DictReader(io.StringIO(text)))
    naive = sum(float(r["amount"]) for r in rows)
    seen, deduped = set(), 0.0
    for r in rows:
        if r["order_id"] in seen:
            continue
        seen.add(r["order_id"])
        deduped += float(r["amount"])
    return naive, deduped, len(rows)

naive, deduped, n = totals(raw)
print("round 1: no duplicate")
print(f"  rows={n}  naive sum=${naive:.2f}  dedup-then-sum=${deduped:.2f}")
print(f"  agree: {naive == deduped}")

raw_with_dupe = raw + "3,carol,20.00\n"
naive2, deduped2, n2 = totals(raw_with_dupe)
print()
print("round 2: order 3 landed twice (simulated webhook retry)")
print(f"  rows={n2}  naive sum=${naive2:.2f}  dedup-then-sum=${deduped2:.2f}")
print(f"  agree: {naive2 == deduped2}")
if naive2 != deduped2:
    print(f"  DISAGREE by ${naive2 - deduped2:.2f} -- that gap is order 3,")
    print("  counted twice. Ship the deduped number, not the naive one.")

That is what an independent second route buys you: it does not need to know what can go wrong, only to be a genuinely different way of getting to the same number.
