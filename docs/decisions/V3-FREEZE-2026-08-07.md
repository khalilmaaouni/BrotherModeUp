## The fourteen freeze answers
1. BrotherMode owns durable project state, decisions, fences, evidence,
   verification semantics, recovery, delivery integrity, coordination law.
2. Claude Code owns model execution, skills, subagents, worktrees, tools,
   session lifecycle.
3. Single source of truth: the SQLite store at .brothermode/store.sqlite3
   behind bm_store service methods. Views (CANVAS, PROJECT-VIEW, status
   cards) are renders, never authorities.
4. Single public runtime boundary: the brothermode CLI (start, status,
   next, review, deliver, view, doctor, recover, version, update). Skills
   call ONLY it. tools/bm_*.py become internal adapters behind it.
5. Single namespace: brothermode (founder decision above).
6. Deterministic: everything the CLI answers (state, evidence existence,
   fence checks, delivery proof, recovery material, version).
7. Model judgment: choosing, planning, review prose, summaries, next-step
   recommendation WORDING (the branch router stays deterministic).
8. Blocking hooks: PreToolUse fence deny; consent gate. These stay
   blocking and synchronous.
9. Informational hooks: telemetry, statusline, autosave notifications;
   may consolidate or go async only where correctness cannot depend on
   them, fail-open policy preserved exactly.
10. Writer isolation: one writer per fence, worktree isolation for
    parallel writers, two active writer worktrees maximum, Fable is sole
    integrator, no writer merges its own branch.
11. Killed-session recovery: store rows plus STATE.md registry plus vault
    session log; the recovery canary must byte-compare restored fixtures.
12. Proof per capability: live installed canary > integration > contract
    > unit > inspection > model judgment. Installed skills proven from a
    fresh throwaway config via the e2e canary (the BM_BENCH_AUTH_CONFIG
    persistent-auth pattern from tonight is the sanctioned auth path for
    every headless canary; its keychain law is measured and documented in
    scripts/benchmark_comparative.py).
13. Temporary v2 compatibility: brotherme marketplace and command names
    as thin shims only if the migration canary needs them; each shim
    carries legacy surface, replacement, reason, test, and removal
    condition (removal condition default: v3.0.0 tag).
14. Compatibility removal: at the v3 release court, every shim without a
    live consumer is deleted; the court fails if an unexplained shim
    remains.
