# BrotherMode + BrotherSBE: Claude Code Startup 10/10 Implementation Blueprint

## 0. Purpose

This document is the execution blueprint for turning BrotherMode and BrotherSBE into a 10/10 engineering operating system for a small startup where Claude Code is the standard development runtime and source control may be GitHub, Bitbucket Cloud, or Azure Repos.

The architecture deliberately keeps BrotherMode and BrotherSBE separate:

- **BrotherMode** owns the developer and Claude Code session lifecycle, local coordination, worktree awareness, agent provenance, local evidence capture, and reliable execution.
- **BrotherSBE** owns the startup-level change, shared risk, policy, evidence validity, team coordination, pull request assurance, provider enforcement, approval state, release assurance, and audit history.
- **GitHub, Bitbucket, or Azure Repos** enforce the final merge decision through native status and policy mechanisms.
- **Claude Fable 5** is the program director and highest-level technical orchestrator.
- **Claude Sonnet 5** is the default implementation worker.
- **Claude Opus 4.8** is the independent reviewer for work where a fresh model context is more valuable than using the same Fable context that planned the work.
- **Fresh-context Fable 5** is reserved for T4 architecture, security, data integrity, and high-blast-radius review where maximum reasoning depth is justified.

The fundamental unit of coordination is not the Claude session, developer, branch, file, or pull request. It is the **Change**.

A Change may contain:

- many BrotherMode sessions;
- many Claude subagents;
- several engineers;
- several worktrees;
- several commits;
- several repositories;
- several pull requests;
- one shared risk and evidence state;
- one final assurance verdict.

# 2. Fable Execution Contract

This section is written as direct operating instructions for Claude Fable 5.

## 2.1 Fable role

Fable is the **Program Director**. Fable owns:

1. WBS sequencing.
2. Dependency resolution.
3. Work-package decomposition.
4. Subagent assignment.
5. Model assignment.
6. Acceptance criteria integrity.
7. Cross-workstream architecture decisions.
8. Escalation of contradictory findings.
9. Milestone gate review.
10. Final release readiness recommendation.

Fable should not implement routine code when a Sonnet worker can execute a sufficiently specified task.

## 2.2 Separation of duties

Fable must preserve these rules:

1. **Planner is not final verifier.** The context that made the architecture decision must not be the only context that certifies the implementation.
2. **One writer per work package.** Only one implementation agent may own a given file set at a time unless the Change Registry explicitly transfers ownership.
3. **Independent verification is read-only.** Reviewer agents do not fix the code they are grading. They return findings to the assigned writer.
4. **No evidence, no close.** A work package cannot be DONE from narrative confidence alone.
5. **Latest change wins.** Evidence that predates a relevant code/configuration change is stale.
6. **Risk floor cannot be silently lowered.** Machine or policy detected minimum risk requires explicit human override with a recorded reason.
7. **Provider adapters cannot redefine policy.** They translate provider semantics only.
8. **Team state belongs to BrotherSBE.** BrotherMode emits events but must not become the shared source of truth.
9. **Local failure must fail safely according to tier.** T0/T1 may degrade with visible warning where policy permits. T3/T4 must fail closed for merge assurance.
10. **Every irreversible or external side effect requires explicit authority.** Merge, deploy, production mutation, credential change, and destructive migration remain human or provider controlled.

## 2.3 Fable task lifecycle

Every work package follows this state machine:

```text
BACKLOG
  -> READY
  -> CLAIMED
  -> IMPLEMENTING
  -> SELF_CHECK
  -> INDEPENDENT_VERIFY
  -> ACCEPTED
  -> INTEGRATED
  -> DONE

Failure paths:
IMPLEMENTING -> BLOCKED
SELF_CHECK -> REWORK
INDEPENDENT_VERIFY -> REWORK
INTEGRATED -> REWORK
Any state -> CANCELLED, only with reason
```

# 3. Claude Model Routing Policy

## 3.1 Default model matrix

| Model | Role | Default use | Do not use as default for |
|---|---|---|---|
| Claude Fable 5 | Program director, principal architect, critical adjudicator | Long-horizon architecture, cross-workstream planning, T4 reasoning, milestone reviews | Mechanical implementation, repetitive tests, bulk adapter boilerplate |
| Claude Sonnet 5 | Primary engineering worker | Implementation, tests, refactors, API adapters, deterministic tooling, docs from accepted design | Sole final reviewer of its own work |
| Claude Opus 4.8 | Independent senior reviewer | Fresh-context code review, threat modeling, architecture challenge, integration verification | High-volume mechanical changes if Sonnet meets quality bar |
| Claude Fable 5 fresh context | Critical independent verifier | T4 migrations, auth, payments, policy engine, event integrity, provider enforcement | Every PR or routine task |

## 3.2 Routing rules by risk tier

| Tier | Planning | Implementation | Verification | Human requirement |
|---|---|---|---|---|
| T0 | Sonnet or Fable batch planning | Sonnet | deterministic tests | none beyond normal repo policy |
| T1 | Sonnet | Sonnet | separate Sonnet reviewer or deterministic verifier | normal PR review if repo requires |
| T2 | Fable or Opus | Sonnet | Opus fresh context | code owner |
| T3 | Fable | Sonnet, with Fable escalation for hard sections | Opus plus targeted Fable review | domain owner + required reviewer |
| T4 | Fable | Fable or Sonnet under narrow spec | Opus plus fresh-context Fable | explicit human approval, domain/security/CTO as policy defines |

## 3.3 Cost and quality discipline

Fable should use the lowest-cost model that repeatedly meets the acceptance bar. Promote work upward only when one of these conditions is true:

- task ambiguity remains after one clarification pass;
- architecture spans more than one subsystem;
- data integrity or security consequence is material;
- implementation worker fails the same acceptance criterion twice;
- reviewer finds systemic rather than local defects;
- provider semantics differ in a way that changes policy meaning;
- the work affects Brother's own enforcement or evidence integrity.

### 5.0 Evidence acceptance rule

A human sentence such as "tests passed" is never evidence by itself. It may be a comment that points to evidence.

# 15. Definition of Done by Change Tier

## T0

A Change is done when:

- affected scope is known;
- configured existing checks are green or explicitly not applicable;
- no detector raises the floor;
- provider policy permits merge.

## T1

A Change is done when:

- relevant tests at current SHA pass;
- normal repository review policy is satisfied;
- evidence is fresh;
- Brother required check passes where configured.

## T2

A Change is done when:

- all T1 requirements pass;
- code/domain owner requirement passes;
- integration evidence exists when behavior crosses module/service boundary;
- no unresolved blocking overlap exists.

## T3

A Change is done when:

- risk floor is accepted;
- targeted and integration evidence is fresh;
- stateful change has rollback evidence or explicit policy-approved alternative;
- cross-repo dependencies are complete;
- required domain owner approval is fresh;
- no provider is using stale PASS;
- post-deploy verification is complete if policy requires it.

## T4

A Change is done when:

- Fable planning is complete;
- implementation evidence is complete and current;
- Opus independent verification passes;
- fresh-context Fable critical review passes;
- required human authorities approve;
- rollback/containment is proven or explicitly accepted by authorized humans;
- merge gate passes on exact head/candidate SHA;
- configured post-deploy health evidence passes;
- any break-glass use has follow-up resolved.

# 16. Failure and Escalation Rules for Fable

Fable must stop parallel execution and escalate when any of these conditions appears:

1. Two work packages require changes to the same core contract.
2. Provider adapters need different core semantics to pass tests.
3. A Sonnet worker fails the same acceptance criterion twice.
4. A verifier finds a P0/P1 architectural defect.
5. Risk eval falls below threshold for any critical class.
6. Evidence freshness can produce a false fresh state.
7. A provider allows merge despite a configured required Brother failure.
8. Event replay diverges from live projected state.
9. A credential or authority path permits spoofed assurance.
10. T3/T4 mode can become merge-ready during Team Plane outage.
11. False block rate exceeds 2% during a pilot window.
12. T0/T1 median developer overhead exceeds 2 minutes for two consecutive measurement windows.

Escalation order:

```text
Worker finding
  -> program-director Fable
  -> principal-architect Fable if contract issue
  -> independent Opus review if disputed
  -> fresh-context Fable if T4 or milestone-critical
  -> human owner if product/policy authority is required
```

# 20. Reference Platform Assumptions Verified for This Blueprint

The following assumptions were checked against current first-party platform documentation on 2026-08-15 and should be revalidated before implementing a provider-specific integration if APIs or product features change.

## Claude Code

Claude Code currently exposes lifecycle hooks sufficient for this design, including pre/post tool hooks, full post-tool batches, session start/end, subagent start/stop, tasks, worktree creation/removal, compaction, configuration/instruction changes, and teammate-idle events. Plugin-distributed agents can specify model, effort, tool restrictions, skills, memory, background behavior and worktree isolation. Command hooks remain the conservative production choice for hard controls, while agent hooks are experimental.

## GitHub

GitHub rulesets can require status checks before merge. A required check can be associated with an expected GitHub App source in supported configuration. This supports a Brother App publishing an assurance status/check and the repository requiring it before merge.

## Bitbucket Cloud

Bitbucket Cloud supports Forge custom merge checks that can be configured as required and can prevent a pull request from merging. Custom checks can be configured at workspace, project, and repository levels with inherited behavior. Commit/build statuses and code insights can provide complementary visibility.

## Azure Repos

Azure Repos supports external pull-request status checks as branch policy. The status can be required, tied to an authorized identity, configured with reset conditions for new changes, and used to block pull-request completion until the external service reports success.

## Claude model routing

Claude Fable 5 is the highest-capability model in the target routing scheme and is suitable for long-horizon program and architecture work. Claude Sonnet 5 is the default high-volume coding/agent workhorse. Claude Opus 4.8 remains a strong complex coding and reasoning model and is deliberately used here as a decorrelated fresh-context reviewer rather than simply assigning Fable to every role.
