## 2. Attack A1: make verify-close PASS over a hollow pack

VERDICT: BROKEN. Eight of eleven hollow packs were declared ready to close.

Fixture per case: one record, parked with a handover heading, `skeleton
--out docs/handover/pack1 --slot pack1 --date 2026-08-11`, every human block
filled, `zip --pack <pack>`, then the mutation, then
`verify-close --pack <pack> --session test-session`.

| case | mutation | exit | verdict |
| --- | --- | --- | --- |
| A1a | human block and both markers deleted from 01-HANDOVER.md | 0 | PASS |
| A1b | human block emptied to whitespace only | 0 | PASS |
| A1c | 01-HANDOVER.md truncated to zero bytes | 0 | PASS |
| A1c2 | all six narrative files truncated to zero bytes | 0 | PASS |
| A1d | 01-HANDOVER.md deleted | 1 | FAIL (correct) |
| A1e | block left saying lowercase `fill-by-hand` | 0 | PASS |
| A1f | close report status is ```` ``` ```` / FINISHED / ```` ``` ```` | 0 | PASS |
| A1g | FINISHED buried on the fourth line under other prose | 0 | PASS |
| A1h | lowercase `finished: all clear` | 1 | FAIL (correct) |
| A1i | bare `UNFINISHED`, no baton location | 0 | PASS |
| A1j | `FINISHEDNESS is a myth and we quit early` | 0 | PASS |

Observed output, the worst case:

```
[A1c2 all six narrative files zero bytes] exit=0
PASS: .../docs/handover/pack1 is ready to close.
```

Why the spec says this is wrong. Section 4 makes verify-close "the mechanical
checklist. FAIL when a narrative slot is still FILL-BY-HAND". The
implementation reads that literally: `cmd_verify_close` check 1 is
`if FILL_BY_HAND in line`, a substring scan of the seven files. Deleting the
marker, emptying the block, or emptying the whole file all remove the
substring, so the cheapest possible way to defeat the gate is to delete the
thing the gate looks for. Section 3 step 1 calls for the closing session to
"fill every narrative slot by hand"; six empty files satisfy the code and not
the rule.

A1f and A1g are judged by section 3 step 2: "The close report opens with one
unmissable line: FINISHED or UNFINISHED". Check 2 is
`any(line.strip().startswith("FINISHED") ...)` over every line in the file, so
the line need not open the report, need not be outside a code fence, and need
not be a whole word. The tool's own generated instruction in `_struct_06`
says "The FIRST LINE must start with the exact word FINISHED", which the code
does not enforce.

A1i is reported as observed, not as a defect: section 4 lists the FAIL as
"when the close report lacks the FINISHED or UNFINISHED line", so UNFINISHED
must PASS, and it does. The spec, not intuition, settles that. The residue is
that section 3 step 2 also demands "if UNFINISHED, exactly where the baton
lies", and a bare `UNFINISHED` with no location still passes.

## 3. Attack A2: unparked records, and a zip older than the pack

VERDICT: BROKEN. Three ways, one of them on the ceremony's own invocation.

### A2a, the headline. The prescribed command never runs the ownership check.

```
record state in store: active
[A2a verify-close (no --session) with 1 ACTIVE unparked record] exit=0
PASS: .../docs/handover/pack1 is ready to close.

[A2a-control same pack WITH --session] exit=1
FAIL: session test-session still owns 1 unparked record(s): fence-alpha (d0caa896)
```

Section 4 lists among the FAIL conditions "when this session still owns
unparked records", and the same section spells the signature as
`verify-close [--pack DIR]`, with no session flag at all. Section 3 step 7,
the rule text a closing session follows, is "Run `python3
tools/bm_handover.py verify-close` and quote its verdict." Run exactly that
way, `session = kv.get("session") or ""` is empty and check 4 is skipped
entirely. The single most important check in the gate is off by default, and
the ratified rule never turns it on. Every session that follows the rule as
written gets a PASS while still holding live fences.

### A2b. Even with --session, only state `active` is caught.

```
record state in store: adopted session: test-session
[A2b --session given, record state=adopted (unparked, owned)] exit=0
PASS: .../docs/handover/pack1 is ready to close.
```

The store's transition table (tools/bm_store.py around line 5554) has
`parked`, `active`, `adopted` and `complete`. Check 4 filters
`r["state"] == "active"`. A record the session adopted and never parked is
unparked and owned, which is the condition section 4 names, and it passes.

### A2c, A2e. COULD NOT BREAK.

A zip belonging to a different slot does not satisfy the check (FAIL, exit 1,
naming the missing `BrotherMode-Handover-pack1.zip`). A pack edited after
zipping is caught (FAIL, exit 1). `_dir_mtime` reading the freshest file mtime
rather than the directory mtime does the job it was written for.

### A2d. Stale zip content passes when the mtime is newer.

Filled and zipped with `FINISHED: all clear.`, then the close report rewritten
on disk to `UNFINISHED: everything is on fire, baton is nowhere.`, then the
zip's mtime pushed 600 seconds forward:

```
[A2d zip mtime newer but content STALE] exit=0
PASS: .../docs/handover/pack1 is ready to close.
   zip still says FINISHED: True | disk says UNFINISHED: True
```

Reported as observed rather than as a clear spec breach: section 4 words the
condition as "when the newest zip is older than the pack", and mtime is
literally what it asks for. The gap is that nothing compares content, so the
archived artefact and the judged pack can disagree.

### A2f. A pack subdirectory is silently dropped from the zip and is invisible to the freshness check.

```
[A2f] zip cmd said: wrote .../BrotherMode-Handover-pack1.zip (7 file(s))
   names in zip: ['pack1/00-READ-ME-FIRST.md', ... 'pack1/06-CLOSE-REPORT.md']
   evidence/gate-receipt.json present in zip: False
[A2f subdir evidence changed after zip] exit=0
PASS: .../docs/handover/pack1 is ready to close.
```

`cmd_zip` filters `os.path.isfile`, and `_dir_mtime` walks only top level
files. An `evidence/` folder inside the pack is never packaged, its later
edits never move the pack's tracked mtime, and the command reports "7 file(s)"
without saying anything was left behind. Section 4 says zip "packages the pack
folder"; it packages the pack folder's top level only, silently.

## 4. Attack A3: make skeleton destroy human text (rule I10)

VERDICT: BROKEN. Four of seven vectors destroyed human bytes.

Sentinels were planted, then `skeleton` was re run over the same pack.

| case | shape | result |
| --- | --- | --- |
| A3a | block contains the literal string FILL-BY-HAND | survived, file byte identical |
| A3b | a second, hand added human block | SENTINEL-TWO destroyed |
| A3c | markers quoted inside the block | text after the quoted end marker destroyed |
| A3c2 | same, two regenerations | same loss, stable thereafter |
| A3d | a stray end marker before the real begin marker | text before it destroyed |
| A3e | human paragraph appended after the end marker | SENTINEL-OUTSIDE destroyed |
| A3f | pack file chmod 400 | exit 0, sentinel survived |
| A3g | pack directory reached through a symlink out of the project | refused, path-escape |

Observed, A3e, the most ordinary of them:

```
[A3e human text appended OUTSIDE the block]
   'SENTINEL-ONE'                     survived=True
   'SENTINEL-OUTSIDE'                 survived=False
```

Why the spec says this is wrong. Section 4: skeleton "Refuses to overwrite a
slot a human already filled (the I10 rule: generated output never destroys
human text)." The tool never refuses anything. It preserves exactly one block
per page, the first one, and rewrites everything else without warning. A
person who appends a paragraph at the bottom of a page, or adds a second notes
section, or quotes the marker while explaining it, loses that text on the next
regeneration and is told `wrote pack docs/handover/pack1` with exit 0.

Note on the divergence that causes A3c: tools/bm_store.py already carries a
marker scanner, `_human_block_spans` at line 17542, which tracks `depth` and
documents that "A second begin marker INSIDE a block is content, not a nested
block". `read_existing_human_block` in bm_handover.py is a second, `inside`
flag implementation of the same idea with different end marker semantics.

A3g is a COULD NOT BREAK worth recording: `bs.safe_project_path` caught the
symlinked parent directory and refused with `path-escape`, writing nothing
outside the project.

A3f is also COULD NOT BREAK, and mildly surprising: a read only pack file is
rewritten anyway (the funnel replaces the file rather than opening it for
write), so the chmod neither blocks the run nor loses the human block.

## 5. Attack A4: make detect lie, or crash

VERDICT: BROKEN on the exit code contract. COULD NOT BREAK on the pasted
clearing command.

### The clearing command is real. COULD NOT BREAK.

detect's printed command was captured from stdout and executed verbatim in a
subprocess:

```
   PASTED: python3 .../tools/bm_store.py handover-ack --handover 5093625fd5234d3eaa6945a52b212ee4
   -> exit=0 out=handover-ack: 5093625fd5234d3eaa6945a52b212ee4 acknowledged; it no longer renders into STATE.md.
```

An empty estate is stated, not silent (`NO-DATA` lines for pack, zip, plus
"unacknowledged handovers: none", "dead-owner leftovers: none"), which is what
section 8's V5 asks for. A broken symlink sitting in docs/handover does not
disturb it (exit 0).

### detect exits 1 with a traceback when a pack directory is unreadable. BROKEN.

Real subprocess, not in process:

```
=== bm_handover.py detect (unreadable pack dir) ===
exit code: 1
stderr tail:     for name in os.listdir(pack_dir):
PermissionError: [Errno 13] Permission denied: '.../docs/handover/pack1'
```

Section 4 is explicit: detect is "Read only, exit 0 always (it informs; the
start half of the rule is what acts)." `_dir_mtime` calls `os.listdir` with no
guard, and `main` catches only `OwnershipRefused` and `BMStoreError`, so an
ordinary `PermissionError` becomes an uncaught traceback. The same call takes
verify-close down as well, where the crash exit code 1 is indistinguishable
from the FAIL exit code 1, so an automated reader sees a failed checklist
rather than a broken tool.

### Not falsified: live versus dead classification.

Every fixture returned "dead-owner leftovers: none". I could not seed a
genuinely dead owning session through the public API within this pass, so
detect's core claim, that it names dead sessions correctly and does not
mislabel a live one, is UNTESTED. Recorded in section 9 as a gap, not as a
pass.

## 6. Attack A5: get founder text onto a pack page or stdout

VERDICT: BROKEN. Three columns the store's own central policy withholds are
written verbatim to pages that are committed to git and zipped for the founder.

Seeded a decision and a parking handover with founder shaped prose, ran
`skeleton`, then compared what `bs.export_column` says against what landed:

```
store policy vs pack page
  decisions.text     export_column='[WITHHELD: 83 chars of founder text]' | verbatim on 01-HANDOVER.md=True
  decisions.topic    export_column='[WITHHELD: 46 chars of founder text]' | verbatim on 01-HANDOVER.md=True
  handovers.heading  export_column='[WITHHELD: 71 chars of founder text]' | verbatim on 01-HANDOVER.md=True
  handovers.heading verbatim on 04-NEXT-LOOPS-PRIORITIZED.md: True

the exact lines written to the committed pack page:
   - `6358e5aa` 2026-08-11T03:22:13Z: whether to tell the investors about the runway (Khalil decided to drop the Siemens account; Marie is being managed out in September)
   - `dd05d06e` lifecycle 6358e5aa at 2026-08-11T03:22:13Z: Baton: the Acme contract is unsigned because the founder is out of cash

shipped zip BrotherMode-Handover-pack1.zip carries decision text: True ; heading: True
detect stdout carries the heading verbatim: True
```

This is the same class as the session id defect that was already fixed, and
the fix's own comment in `_gather` states the reasoning that convicts the
remaining three fields: "The display value comes from bs.export_column, the
store's OWN central withholding policy, rather than from _scrub or from any
rule restated here: _scrub covers secret shapes and absolute paths, and a
plain hand-typed id is neither, so it went straight onto the page." A decision
text, a decision topic and a handover heading are likewise neither secret
shaped nor absolute paths. `_gather` sends all three through `_scrub` alone,
so `export_column`'s default deny for text columns is bypassed. Section 4
constrains the tool to read the store "read only through bm_store's public
functions"; it does read through them, and then overrides the policy those
functions exist to apply.

`records.name` and `claims.path` were checked in the same run and are correct:
`export_column` classifies both as scrub only, which is exactly what `_scrub`
does, so those two agree with policy.

Secondary, lower severity: absolute paths are not masked in the tool's own
stdout.

```
verify-close stdout: PASS: /var/folders/.../project/docs/handover/pack1 is ready to close.
mask_absolute_paths would have rendered it as: PASS: [PATH WITHHELD] is ready to close.
```

detect prints the same unmasked absolute paths for the newest pack and zip. On
a real machine those carry the founder's home directory layout, and the rule
asks for these verdicts to be quoted into session logs and packs.

## 7. Attack A6: write outside the pack directory and the handovers directory

VERDICT on the stated property: COULD NOT BREAK. Every write landed inside the
project root or inside the handovers directory.

| case | attempt | result |
| --- | --- | --- |
| A6a | `skeleton --slot ../../../../../../tmp/evil-slot` | exit 2, refused path-escape, /tmp/evil-slot not created |
| A6c | `skeleton --out docs/../../escaped` | exit 2, refused path-escape |
| A6b | `skeleton --out /tmp/abs-out-evil` | exit 0, landed at `<root>/tmp/abs-out-evil`, nothing at /tmp |

`cmd_skeleton` strips leading slashes and splits, so an absolute `--out` is
silently reinterpreted as relative to the root rather than refused. Containment
holds; the silence is the only complaint. The zip destination cannot escape
either: `_zip_path_for` uses `os.path.basename` of an absolutised path, which
cannot resolve to `..`.

Adjacent property, and here it is BROKEN: `zip --pack` accepts any absolute
directory with no containment check at all, and packages it into the founder's
handovers archive.

```
[A6d zip --pack <arbitrary dir outside the project>] exit=0
   stdout: wrote .../handovers/BrotherMode-Handover-fake-dot-ssh.zip (2 file(s))
   contents: ['fake-dot-ssh/config', 'fake-dot-ssh/id_rsa']

[A6e zip --pack <project root>] exit=0
   contents: ['project/secrets.env']
   secrets.env bytes in zip: b'CREDENTIAL_PLACEHOLDER=not-a-real-value\n' (the fixture was de-keyed after this run; the finding is unchanged)
```

`cmd_skeleton` routes its path through `bs.safe_project_path`; `cmd_zip` and
`cmd_verify_close` call `os.path.abspath(kv["pack"])` and nothing else. A
mistyped or hostile `--pack` copies arbitrary directory contents, unredacted,
into ~/Documents/BrotherModeUp-handovers. The archive is the one artefact the
ceremony hands the founder.

## 8. Second discovery round

Run because one round of findings is not evidence that the surface is
exhausted. It produced four more results, so a third round would be justified

### R2a. The command centre copy is never checked. False PASS.

```
[R2a] command centre copy present in pack: False
[R2a pack with no command-center copy] exit=0
PASS: .../docs/handover/pack1 is ready to close.
```

Section 3 step 1 defines the pack as the six files "plus 06-CLOSE-REPORT and a
copy of the command center page". verify-close iterates `PACK_FILES`, which
holds seven entries and not the command centre, so a pack missing the page the
rule names passes.

### R2b. Seven symlinks to one decoy outside the project. False PASS.

Every pack file was deleted and replaced with a symlink to a single file
outside the project reading `FINISHED: nothing to see here.`

```
[R2b all seven pack files are symlinks to one decoy outside the project] exit=0
PASS: .../docs/handover/pack1 is ready to close.
```

`os.path.isfile` follows symlinks and verify-close applies none of the
containment `safe_project_path` gives skeleton. The zip then packages the
decoy's bytes under the pack's names.

### R2c. COULD NOT BREAK.

With a filled and zipped pack made the newest and a hollow pack belonging to
the session, `verify-close` with no `--pack` judged the newest pack and
returned FAIL, exit 1. It refused for the zip freshness reason rather than
noticing the hollow pack, but it did not falsely pass.

### R2d. A permanent deadlock: the ceremony can become unclosable.

Zip an unchanged pack, then re save the pack files with identical bytes (any
editor or formatter that rewrites in place). The pack mtime advances, the zip
content does not change, so `cmd_zip` takes its idempotence branch, removes
the temp file and leaves the existing zip's mtime untouched.

```
attempt 1: zip -> zip unchanged: .../BrotherMode-Handover-pack1.zip
            verify-close -> exit=1 FAIL: the zip ... is older than the pack ...
attempt 2: zip -> zip unchanged: .../BrotherMode-Handover-pack1.zip
            verify-close -> exit=1 FAIL: the zip ... is older than the pack ...
attempt 3: zip -> zip unchanged: .../BrotherMode-Handover-pack1.zip
            verify-close -> exit=1 FAIL: the zip ... is older than the pack ...
```

The FAIL message instructs "run `... zip --pack ...` again", and running it
again can never clear the condition. Section 3 step 7 says "A FAIL means the
ceremony is not done; the session does not claim closure", so a session in
this state cannot lawfully close by any route the rule offers. This is a false
FAIL, not a false PASS, but it is the one defect that stops the ceremony
outright.

  fixture returned "dead-owner leftovers: none" and I did not find a way to
  seed a genuinely dead owning session through the public API inside this
  pass. The `bm_stall.sweep` rendering path in `cmd_detect`, including whether
  `f["message"]` and `f["name"]` arrive scrubbed, is therefore UNVERIFIED.

  ~/Documents/BrotherModeUp-handovers. The brief is read only over the working
  tree, so every fixture was synthetic.
- The full gate, tools/test_all.py. Only tools/test_bm_handover.py was run, as
  the baseline. Section 8's CLOSE item is unproven by this pass.
- Concurrency. Two sessions running skeleton or zip against one pack at the
  same time was not attempted.
- `bs.write_generated_document` internals, including whether its own redaction
  funnel touches the structural sections. I tested what reaches the page, not
  how it gets there, so a leak introduced inside the funnel would not have
  been caught here.
- Filesystems with coarser mtime granularity than APFS. Every freshness result
  in section 3 depends on sub second mtime resolution and may behave
  differently elsewhere.
- A third discovery round. The second round produced four new findings, so by
  the two quiet rounds standard the surface is not yet exhausted.
