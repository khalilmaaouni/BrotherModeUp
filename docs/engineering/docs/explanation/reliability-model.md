# Reliability Model and Boundaries

BrotherMode's engineering value comes from mechanisms that sit around model behavior. This page states what each mechanism is intended to guarantee and where the boundary stops.

## Reliability Layers

| Layer | Mechanism | What it helps prevent | Important boundary |
| --- | --- | --- | --- |
| Memory | Durable project records | Reconstructing state from chat memory | Records are only as good as what gets recorded |
| Coordination | File claims/fence | Two cooperating Claude sessions silently overwriting supported writes | Not an OS sandbox; shell coverage is partial |
| Verification | Review/evidence | Calling work done without checks | Does not prove test strategy is sufficient |
| Delivery | Delivery gate/packet | Handoff without verification context | Packet proves recorded evidence, not every possible property |
| Continuity | Handoff packet and successor launch | Work stopping because one session ended | Process liveness is not comprehension |
| Recovery | Autosave snapshot path | Losing everything at context/session interruption | Snapshot-based, not continuous backup |
| Visibility | Status and project view | Human cannot tell where work stands | HTML view is a snapshot |

## Mechanical vs Behavioral

Some BrotherMode properties are mechanical:

- a command reads project records;
- a supported foreign write is refused by a hook;
- a delivery packet is generated by code;
- Doctor returns PASS/FAIL/SKIP checks;
- a continuation launch can record process liveness.

Other properties still depend on model/developer discipline:

- choosing a good task boundary;
- writing the correct acceptance criteria;
- choosing sufficient tests;
- deciding that a human decision is resolved;
- invoking continuation when a workflow is ending outside a mechanically wired path;
- interpreting project risk correctly.

Do not describe behavioral discipline as a hard technical guarantee.

## Shell Write Boundary

BrotherMode's strongest prevention applies to supported Claude Code write tools and recognized write shapes. Other shell/external writes can fall into detection rather than prevention.

Engineering consequence:

- use BrotherMode-supported edit paths for coordinated parallel work;
- investigate bash-audit alerts;
- do not claim hostile-process isolation.

## Runtime Boundary

BrotherMode's enforcement is verified for Claude Code.

A different agent runtime can still read BrotherMode instructions or use parts of the CLI, but that does not imply Claude Code hooks execute there.

Treat cross-runtime behavior as separate evidence, not a transitive guarantee.

## Recovery Boundary

The recovery path operates on BrotherMode autosave snapshots taken at defined boundaries.

It is not equivalent to:

- continuous filesystem backup;
- cloud backup;
- Git commits after every write;
- recovery from deleted `.git` metadata.

Use normal backup/version-control practices in addition to BrotherMode.

## Evidence Boundary

Evidence answers:

> What check was recorded as having run, and what did it report?

Evidence does not automatically answer:

> Was this the right check for the risk?

The development team remains accountable for test design and release policy.
