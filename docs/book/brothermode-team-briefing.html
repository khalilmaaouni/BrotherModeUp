Part zero

The two pages everyone should read

Stop after this section and you will still know what BrotherMode is, what it costs you, and whether your next piece of work should use it. Everything after this is depth to reach for when you need it.

In one paragraph

BrotherMode is not a prompt pack and it is not a smarter model. It is a set of working rules for a Claude Code session, plus the small toolchain that holds the session to those rules, plus the record that outlives it.

Installed, it changes three things about how Claude works on your repository. It agrees the shape of the work with you before it touches anything. It claims a file before writing to that file, and a second session reaching for a claimed file is refused by a program rather than by a polite reminder in a prompt. And it will not use the word done until a check has run after the last edit and passed, with the command quoted back to you.

Everything else in this booklet sits underneath those three sentences.

SKILL.md holds the law. tools/bm_fence_hook.py is the program that refuses. references/definition-of-done.md is the fifteen-point list that decides what done means.

The five failures it exists to close

Nothing in this system is there because it sounded wise. Every rule is in the file because its absence already cost somebody a real afternoon. These are the five, and they are the honest reason to care.

FailureWhat it looks like on a normal dayWhat closes it
AmnesiaA new session re-explores what yesterday's session already knew, and you pay for the same reading twice.A record on disk, read at the start and written at the close.
CollisionTwo agents edit one file. The slower one wins. The other one's work is simply not there any more, and nothing announced it.One writer per file, claimed before the write, refused by a hook.
DisproportionFive subagents dispatched at a one-line question. Or one blind pass at a full audit.A three-question triage, and a declared effort tier in every brief.
Unearned confidenceThe word done with no command behind it. Numbers that were never derived twice.A verifying command after the final edit, quoted. Ranges rather than single-point estimates.
Groundhog dayThe same mistake paid for twice, because the first time was never written down anywhere the next session had to trip over it.A mistakes ledger and a failures index, read before working in an area.

The three layers, and why the order matters

What it costs you, and the gap you should know about first

Bad news before good news is a rule this system applies to itself, so here it is at the front of the booklet rather than buried in an appendix.

The largest gap, stated plainly

This system has been used for real work. It has never been measured on a real project. There is no counted project, no recorded rework rate, and no comparison against working without it. Any productivity number you are ever shown for BrotherMode is invented, including one from me.

docs/KNOWN-LIMITS.md, section "Used for real, but never MEASURED on a real project". docs/NOT-FINALIZED.md item 1.

The other costs are ordinary and you will feel all of them in week one.

  • Tokens and time. Ceremony, verification and independent review are not free. On a one-line edit the overhead is pure waste, which the system itself scores as a failure mode called overthought.
  • Twenty minutes a week from a human. The learning loop only closes if somebody runs the weekly review. Skip it and the loop silently stops, and what you are left with is a long prompt with extra steps.
  • Defaults calibrated on one machine. Every threshold in the file was measured on the author's laptop. Re-measure on yours before treating any of them as physics.
  • Enforcement only on Claude Code. Elsewhere the same rules ship as instruction files that nothing enforces. One runtime, the OpenAI Codex command line, was actually measured, and the answer was no: a live run overwrote a file another session had claimed, twice.

docs/DESIGN.md section 9 states the tradeoff in the author's own words. docs/RUNTIMES.md carries the per-runtime table. docs/mistakes/M19-the-codex-fence-does-not-fire-in-exec-mode.md records the measurement.

A rule in a prompt is not a control. A control is a check that runs.The sentence the whole system is built around

When to skip it entirely

This is the section most tools do not write. Note that the industry's own standard README template treats a limitations or when-not-to-use section as optional guidance inside the project description. Here it is structural, and it sits on page two rather than in an appendix.

Reach for it when any of these is true

  • The work spans more than one session, so something has to survive between them.
  • More than one agent or session could touch the same files.
  • A wrong number costs money, or a wrong claim costs credibility.
  • The step is irreversible: a release, a migration, a deletion, a publish.
  • Somebody who was not in the conversation will have to pick the work up later.

Do not reach for it when

  • It is a one-shot question with a self-contained answer.
  • It is a throwaway script nobody will run twice.
  • You are brainstorming, and verification ceremony would kill the momentum.
  • Nobody on your team will ever run the weekly review. The loop is the point; without it you pay the overhead for nothing.

docs/DESIGN.md section 10 states both lists.

That is the two pages. Everything below is reference.

Part one

Your first hour

Install it, prove the install works, run one real project through to a delivery packet. An hour is honest for the first time, and about ten minutes every time after that.

Install: two paths, and which one you want

The plugin path is two lines and no folders to manage. The pinned clone is the path proven end to end the most times, and it is what an auditor should use, because it pins an immutable tag rather than a moving branch.

The plugin path

claude plugin marketplace add khalilmaaouni/BrotherModeUp@v3.0.0
claude plugin install brothermode@brothermode-marketplace

Those are plain shell commands and you paste them into a terminal once. The @v3.0.0 matters: it pins the marketplace to the released tag instead of the repository's moving default branch. The hook groups register on the next start.

The whole path runs on every release inside a throwaway configuration via scripts/release-smoke-install.sh: marketplace add, install, installed version matched against VERSION, every hook group registered, then a clean uninstall leaving settings untouched. A release whose smoke run does not print PASSED does not ship.

The thing that trips people

The desktop app cannot run the /plugin slash command itself. Run the two lines above in a terminal once, and the desktop app then consumes the installed plugin normally. Reproduced against the desktop app on 6 August 2026.

The pinned clone

git clone --branch v3.0.0 --depth 1 \
  https://github.com/khalilmaaouni/BrotherModeUp.git \
  ~/.claude/skills/brothermode

Do not run both paths on one machine. The plugin wires the same hook events the clone's installer wires, so a machine carrying both runs every hook twice. Pick one.

Then prove it is actually wired

python3 scripts/doctor.py

Ten checks, each read-only, each printing PASS, or FAIL with one plain-word fix, or SKIP with the reason nothing could be checked. The deepest of the ten is the one worth watching: it proves the fence is live on your machine by simulating a blocked foreign write and an allowed owner write inside a throwaway project. A check that crashes becomes its own FAIL naming the exception, so one broken check cannot hide the other nine.

scripts/doctor.py, table in docs/SETUP.md. Reachable from inside a session as /brothermode:doctor.

Requirements, in full

  • Claude Code, terminal or desktop, with skills enabled.
  • Python 3.9 or newer, standard library only. There is nothing to install with pip.
  • git.

No account, no server, no subscription, no API key of its own. The tools make no network calls, and that claim is checkable in under a minute rather than taken on faith:

grep -rnE "^[[:space:]]*(import|from)[[:space:]]+(urllib|http|socket|requests)" tools/*.py
# expect no output

The ban is enforced on every shipping module by tools/test_bm.py, so it cannot regress quietly. The only thing that shells out at all is the autosave mechanism, and it only ever calls local git.

Your first project, six moves

Run these from inside the project folder you actually care about, not from the BrotherMode folder.

One
/brothermode:start followed by your goal in your own words. It asks only the questions whose answers change the scope, one decision at a time, recommended option first. It ends with a written brief, a first decision, and a time and cost range given as a range rather than a promise.
Two
/brothermode:status prints goal, direction, progress, time remaining, decision needed, risk, evidence, next step. Every field computed from the records. A field the records cannot answer says so in its own words rather than being smoothed over.
Three
/brothermode:next recommends one step and says why that one. When a decision from you is what blocks progress, it brings you the decision instead of inventing work around it.
Four
Work happens. Before any part of the session writes to a file, the claim is recorded. A second session that tries to write a claimed file is refused by a hook.
Five
/brothermode:review checks the work against the definition of done and reports what passes and what does not, failures first, each point carrying the evidence that proves it.
Six
/brothermode:deliver writes the delivery packet from the records. If a check is missing or failing it says so and lists what remains, instead of delivering.

Nothing in that sequence asks you to read a log.

The six events: what actually runs on your machine

This is the part that separates BrotherMode from a document. A hook is a program Claude Code runs at a lifecycle moment. The installer wires programs to six events. One of them can say no.

EventProgram and roleLimit
PreToolUse bm_fence_hook.py. The one hook that can refuse. It blocks a write to a file another live claim covers, whether the write arrives as an Edit, Write, MultiEdit or NotebookEdit call, or as a readable apply_patch envelope on the Bash leg. By default it fails open and says why, so a refusal always means a genuine ownership conflict rather than a broken hook. It does not gate arbitrary shell writes. certified
PostToolUse bm_bash_audit.py. Detects a shell write that crossed a claim. Detection, not containment. It tells you afterwards. It did not stop it.
SessionStart bm_sessionstart.sh. Injects the compressed law, any overdue-review nag, and a recovery pointer after a compaction. A shell script, and the one hook whose cost has not been measured.
PreCompact bm_autosave.py. Snapshots your whole working tree, untracked files included, into a private local git reference right before context is compacted. A rescue, not a backup service. It lives in your own .git and goes when that goes. Never pushed. certified
Stop bm_telemetry.py stop-warn and companions. Checks whether the half-hour catch-up is due, and writes nothing when it is not. It cannot fire inside a turn that never ends. Its activity ceiling is a chosen constant rather than a measured one. beta
SessionEnd bm_telemetry.py outcomes-append. Writes what the session actually cost in tokens, tool calls and time. Nothing is recorded until you consent. The gate is enforced by a test that drives every hook-wired command against a fresh home directory and fails if any of them writes first. certified

Read from hooks/hooks.json. python3 tools/bm_project_facts.py --field hook_events prints the six events. docs/HOOKS.md states what each program receives and the exact contract the fence implements. tools/test_bm_fence_hook.py holds the refusal behaviour in place; tools/test_bm_consent.py holds the consent gate.

What a refusal looks like from the inside

Two sessions are open on one repository. Session A claimed src/pricing.py ten minutes ago and is still working. Session B, which knows nothing about session A, decides that file needs an edit.

Session B's write does not land and then get reverted. It never lands. The hook returns a refusal before the tool call executes, naming the file and the claim covering it, and session B is told to coordinate. The honest thing about that message is that a Python program with an exit code produced it, not a model choosing to be careful.

The residual risk, stated rather than implied: a plain shell write, an echo into that file from Bash, is not gated. It is detected afterwards by the audit hook. Hooks are cooperative enforcement. There is no container and no operating system sandbox here.

The five workers, and how work reaches them

Work is routed by what the task needs, never by a hard-coded model name. Five worker profiles ship as native agents, each with its tier and its rights already set. Three of the five cannot write files at all, which is a design choice rather than an omission: a reviewer that can edit is not a reviewer.

The ladder that decides whether a worker is dispatched at all

Not everything is an agent. The session climbs this ladder and stops at the first rung that suffices, which is the mechanism keeping a simple question from becoming a fleet.

  1. Answer directly from knowledge, currency-checked when the fact could be stale.
  2. One search or documentation lookup, when a fact is verifiable in one pass.
  3. Ask you, when the call is yours, or when your one-minute answer saves an hour.
  4. Work inline, when the task is one file, one seam, one decision.
  5. One worker, for isolated, parallel or context-heavy work.
  6. A fleet, only for genuine scale.

Concurrency is capped from lived evidence rather than optimism: one writer per claim, at most three live claims in a shared tree, at most three concurrent workers when builds are involved and six for read-only fleets, exactly one full test suite at a time, exactly one thing driving a graphical application at a time. Parallel writers beyond the shared-tree cap get their own git worktree, which turns the claim from a convention into a mechanism.

references/delegation.md carries the ladder, the caps and the measurement behind them: four of six workers died at the caps on the author's machine, where one simulator and one build database serialise everything.

The vault is plain markdown on purpose. It survives every tool change, diffs cleanly in git, and stays legible to a human at two in the morning. It is also an Obsidian vault with no configuration at all: open the folder and the links become clickable and the graph draws itself.

Three disciplines keep it useful rather than hoarding. Recall is a query, not a tour, so a session reads what the task needs and never the whole vault. Superseded notes move to an archive with a pointer left behind, because a memory system that only grows becomes noise itself. And notes link to what they build on or contradict, so recall follows edges instead of scanning folders.

docs/DESIGN.md section 4 states the layout and the reasoning. vault-template/ ships the folder ready to copy.

Certified, beta, experimental, unsupported

Every capability carries one of four states, and these are not marketing adjectives. They are read out of a register file, and a test fails the documentation when a page and the register disagree. That is the mechanism stopping a claim from quietly drifting out of the page it was written on.

StateMeans
certifiedProven in the tree today by the named evidence.
betaReal, with a named gap. The gap is written down beside it.
experimentalBuilt or planned, not measured. Read this as: no number exists.
unsupportedNot offered, and no plan makes it offered.

The register's own headlines, as of 6 August 2026. Read this before building an expectation on top of anything.

Certified

  • Single writer per file for the supported write tools, refused by a hook. Other writes are detected, not contained.
  • A durable local store that survives a crash and can be recovered, with its suite running on Linux, macOS and Windows.
  • Current pages held to facts read out of the tree, so a stale count or a stale version fails the build.
  • The guided beginner flow on Claude Code.
  • Continuous integration on macOS and Linux, with fail-fast disabled so one platform cannot erase another's result.
  • Telemetry recorded only after you consent.
  • Two-command plugin install, proven end to end on every release.

Beta, each with its gap

  • Windows. Only the store suite runs there. The installer refuses Windows and WSL works. There is no native Windows install lifecycle.
  • The autonomy contract and the durable controller. Both measured, both tested across three operating systems, both carrying their own list of what they do not yet do, and neither piloted outside this project.
  • The decision record and the catch-up built from it. Holds judgement rather than measurement, and no continuous integration run covers it yet.
  • Handback and handover packs. Enforced by a refusal rather than a convention, and never used by anybody outside the project.
  • The project page. The file on disk is proven. Publishing it as a shared page needs a paid plan and four further conditions, and that half is a separate promise.
  • The hook cost measurement. Real, on one machine, one operating system, one Python version. Every published total is a lower bound, and the page names what was not measured rather than estimating it.

Experimental, meaning not measured

  • Delivering a web build through the guided flow.
  • Deployment previews attached to a delivery.
  • The benchmark harness that would let anyone compare runs. The method is written down. No run against the current tree is recorded, so no current number is claimed.

Unsupported, and on no roadmap

  • Publishing to production on its own. Cutting and publishing a release is a human-gated sequence, and the suite skips the release checks until a human has cut the tag.
  • Spending money on your behalf. There is no account and no server.
  • Legal or security certification of any kind.
  • Replacing a human specialist review.
  • Multi-user or enterprise project management. No shared server, no accounts, no coordination layer across people.
  • Changing its own safety rules.

The register is capabilities.status.json. The block in README.md is generated from it by python3 tools/bm_docs.py capability-status --write, and tools/test_bm_docs.py fails if the two disagree. To change what any of this says, you change the register, not the page.

Part three

Why not just another plugin

The honest answer needs three things: what a plugin can be, what almost all of them choose to be, and where the good ones genuinely beat this one. Everything said about a peer is a desk assessment read from that project's own public material, because no file in this repository can carry evidence about a codebase it does not own.

What a Claude Code plugin can contain

Per the official documentation, a plugin is a directory that can ship any of: skills, custom agents, hooks, MCP servers, language server configurations, background monitors, executables added to the shell path, and default settings. That is the full palette available to every plugin author, BrotherMode included.

code.claude.com/docs/en/plugins, read 8 August 2026. The plugin structure table names each directory and its purpose.

The axis that actually separates them

Nearly every plugin in the ecosystem spends that palette on capability. More commands, more specialist agents, more integrations, more things Claude can now reach. That is a good trade, and it is why the ecosystem is worth having.

BrotherMode spends it on constraint and continuity. It adds one program that can refuse a tool call, and a record that outlives the session that wrote it. Those are the two things a session cannot give itself, because a session cannot remember what it never wrote down, and cannot be stopped by a rule it is also the judge of.

Named, with one genuine strength each

Every one of these beats BrotherMode at something. Read the middle column as true, not as politeness.

PeerWhat it does betterWhat BrotherMode holds instead
Superpowers Enforces a strict test-first, red-green-refactor cycle as a Claude Code skill, refusing code written before a failing test exists. On that one practice it is stricter than BrotherMode's broader law set asks for by default. A wider law covering memory, delegation, honesty and delivery, at the cost of that single-practice sharpness.
BMAD-METHOD Around twenty specialist role personas covering a fuller software lifecycle, on workflows tied to no single model or editor. Five worker profiles and a ladder that often decides not to dispatch at all.
Cline Lives in the editor with plan and act as separate modes, human approval at every step, and model access through more than two dozen providers on your own key. Deeper gating on one runtime rather than shallower reach across many.
OpenHands Runs agent actions inside a sandboxed container by default rather than your own shell, so a task that goes wrong is contained rather than free to touch the host. Cooperative hooks with no sandbox. This is a real gap, not a stylistic difference.
Open GSD Drives its phase loop across several different agent command lines, so a team split across tools can share one process without standardising on a vendor. Enforcement verified on exactly one runtime, and advisory files everywhere else.
Ruflo Coordinates many specialist agents at once with memory shared across the group, so genuinely parallel specialist work does not serialise through one session. Hard concurrency caps taken from measured failures, which cost parallelism on purpose.
Hosted builders The fastest path from a sentence to a running link. Nothing to install, and the deploy button sits in the same window as the build. Everything on your disk, in your repository, under no account and behind no credit meter. There is no BrotherMode hosting and no deploy button at all.

The five things it gets mistaken for

Each of these shares real surface with BrotherMode, which is why people reach for the comparison. Each paragraph gives the difference and what the other thing does better.

Not merely a prompt pack

A prompt pack is a folder of instructions a model reads and, at its own discretion, follows. BrotherMode's laws start the same way. The parts that matter most are not left to discretion: the single-writer rule is refused by a program, and the evidence rules the documentation is held to are checked by a test rather than trusted. A prompt pack is lighter to read, easier to fork line by line, and asks nothing of your machine beyond the words in the file.

Not merely a methodology

A methodology is a way of working somebody has to choose to follow each time. BrotherMode borrows the same shape and wires the parts a methodology leaves to discipline into code and continuous integration. A methodology travels to any tool, any model, any language, because it is only ever an idea written down. This enforcement is specific to one codebase and one hook surface.

Not merely an agent runtime

A runtime reads a prompt, takes actions and stops. BrotherMode runs on top of one rather than replacing it, and adds what a runtime does not supply: state that survives a crash, a registry that stops two sessions clobbering one file, and telemetry written by hooks rather than by the model, so the record cannot be flattered by the thing being graded. A runtime is more flexible and carries none of this overhead, which makes it right for tasks these laws were never written for.

Not merely a hosted app builder

A hosted builder runs the agent in the vendor's environment and hands back a deployed result. BrotherMode runs locally: every artifact, every decision record and every commit stays on your disk, in your repository. The hosted builder is faster to a live URL by a wide margin. Owning the artifact and owning the deploy step are the same tradeoff pointed in opposite directions.

Not merely a project manager

A project manager tracks work somebody else does. Here the same session that writes the plan also writes the code, runs the check, and updates the record from what the check actually said, so the tracking is a byproduct of doing the work rather than a second layer somebody keeps in sync by hand. A project manager is far better at coordinating several people, which is explicitly out of scope here.

The structural argument, borrowed from people who write documentation for a living

Three outside references shaped this booklet, and they are worth knowing because they are also a fair way to judge it.

  • Diátaxis separates documentation into four modes, tutorials, how-to guides, reference and explanation, and argues that mixing them is what makes documentation fail, because each mode serves a need the others conflict with. Django, Canonical, Cloudflare and Gatsby reorganised around it. Part one of this booklet is the tutorial, part four is how-to, parts two and seven are reference, and parts zero and three are explanation. They are kept apart on purpose.
  • SQLite's guidance on when to use it is the model for part three. Three sections: where it works well, where something else may work better, and a checklist that ends by choosing a default. It is the most respected honesty structure in the field, and it works because the negative section is not a disclaimer, it is a decision aid.
  • The Good Docs Project's README template is the interesting one, because it treats a limitations or when-not-to-use note as optional guidance inside the project description. That is the industry standard. Making it structural, and putting it on page two, is a deliberate departure.

diataxis.fr, sqlite.org/whentouse.html, thegooddocsproject.dev/template/readme. All three read 8 August 2026.

Your checklist for choosing

Four questions, in order

  1. Will more than one session or agent ever touch these files? Yes: you want the refusal. No: keep reading.
  2. Will this work outlive one session? Yes: you want the record. No: keep reading.
  3. Does being wrong here cost money, credibility, or a rollback? Yes: you want the verification gate. No: keep reading.
  4. Will anyone run the weekly review? No: use something lighter. The loop is the point.

Four noes means use a lighter tool, and spend the overhead somewhere it buys you something.

Part four

Six projects, end to end

One walkthrough for each kind of work the law recognises. Find your own job here.

BrotherMode does not treat all work the same. It picks the closest work profile at the start, and the profile sets which roles are at the table, which gates apply, and what counts as evidence. Six profiles ship, and the six walkthroughs below are one per profile.

references/profiles.md section 1 defines all six profiles with their default roles and gates.

A numbers project

Data and financial analysis

A commercial analysis whose output is a set of figures somebody senior will act on. The failure mode here is not a crash. It is a number that is quietly wrong, presented with confidence, and repeated in three decks before anybody checks it.

At the table
Scientist, Analyst, senior Data Engineer, senior Data Product Manager. Four, on purpose, because a number that survives four different kinds of scrutiny is a different object from a number one person produced.
The gates
Never rebuild what the manifest says exists. Describe the schema and sample five rows before touching an unfamiliar table. Every headline number independently second-checked before it is shown, not after somebody asks. A numbers manifest per deliverable, re-run and compared before delivery.
The benchmark
A hostile board review. The question is not whether the number is defensible to you, it is whether it survives somebody trying to break it.

The sequence

  1. /brothermode:start with the actual question, in business words. Kickoff asks only what changes scope: which period, which grain, which source is the system of record when two disagree.
  2. The first decision card arrives before any query runs. Usually it is the grain, because getting that wrong invalidates everything downstream and it is cheap to settle now.
  3. Exploration runs read-only. Describe the tables, sample five rows, and use the column names that came back rather than the ones anybody expected.
  4. Each headline figure is computed, then computed again by an independent route: a different query, a row count, or one example checked by hand. A figure that cannot be second-checked in the time available is labelled unverified at the number itself, never in a footnote.
  5. /brothermode:review applies the definition of done. Three points bite hardest here: verification ran after the final edit, an independent reviewer looked at substantial work, and remaining uncertainty is stated rather than implied.
  6. /brothermode:deliver writes the packet. It refuses the words ready to deliver unless every acceptance check has evidence produced after the final edit.

The failure this prevents

A headline figure shown once, then found wrong two weeks later, after it has been quoted in three places. The second-check rule is not thoroughness for its own sake. It is the cheapest possible moment to catch a wrong number, and the cost of catching it later grows with every slide it appears on.

Honest limit here

Nothing in BrotherMode checks your SQL. It enforces that a second derivation happened, that the two agreed, and that an unverified number is labelled. Whether the second derivation was a genuinely independent route is a judgement it cannot make for you.

A website

Design and creative

A marketing site or a small product site: real copy, real images, a real deploy at the end. The failure mode is a session that reads its own CSS, decides it looks right, and ships something nobody looked at.

At the table
Designer, Product, Architect.
The gates
The project's own design grammar beats generic taste. Every visual specified precisely enough to build without interpretation. Motion honours a reduced-motion preference honestly. And the one that matters most: verify by looking at rendered output, never by reading code.
The benchmark
The most beautiful references in the category, named before work starts rather than after.

The sequence

  1. /brothermode:start with what the site is for and who it is for. Kickoff pushes for the decisions that change scope: how many pages, whose brand rules apply, what has to stay editable later.
  2. References are named up front. A benchmark chosen after the work exists is a justification, not a benchmark.
  3. Build runs with one writer per file. If two people or two workers are on it, one owns the stylesheet and one owns the templates, disjointly, and the fence refuses an overlap rather than merging it badly.
  4. Verification is visual. The page is rendered, a screenshot is taken, and what is on screen is described. Reading the code and concluding it looks right is a named violation.
  5. /brothermode:review, then /brothermode:deliver. The packet carries the checks that ran after the last edit.

Honest limit here

Delivering a web build through the guided flow, and attaching a deployment preview to a delivery, are both marked experimental in the register, which here means exactly one thing: not measured. The pieces work. Nobody has counted a web delivery end to end. If a live URL tonight is the whole goal, a hosted builder gets you there faster, and this booklet said so on page two.

A product feature across several sessions

Product build

A feature in an existing application, big enough to span days and more than one working session. This is the case BrotherMode was built for, and the one where the overhead most clearly pays.

At the table
Architect, Product, Designer, Safety, Project lead.
The gates
The repository's documented build and test commands, copied verbatim rather than invented. Zero new warnings. Screenshot or recording proof for anything visual. Safety and privacy invariants re-verified whenever touched. One health check at a stated interval after release, because shipped is not the end of the loop.
Extra laws
Single-writer claims. Human gates on releases, signing and project-file surgery. Every user-facing string through the project's translation contract, with all locales in the same change.

The sequence, and where the session deaths happen

  1. Day one: /brothermode:start, the brief, and the first architecture decision recorded with its alternatives and the condition that would flip it.
  2. Work proceeds. Context fills. Right before it is compacted, the whole tree including untracked files is snapshotted to a local git reference.
  3. Day two, a fresh session: /brothermode:status. Eight fields read out of the store. Nothing reconstructed from a conversation that no longer exists.
  4. Day three, the session is killed mid-task. The next one resumes from the state file and the store, not from recollection, and the recovery pointer says where to look.
  5. Day four, parallel work. Two claims, disjoint file sets, both registered before either worker launched. Fence then dispatch, never the reverse.
  6. /brothermode:review, then /brothermode:deliver, then the post-release health check at the interval stated when the work started.

The failure this prevents

Day three's kill costing day three. It should cost minutes. That is the entire argument for writing state to disk instead of holding it in a conversation, and it is the one benefit every developer feels within a week.

Research and strategy

Research and strategy

A deep dive ending in a recommendation somebody will act on. The failure mode is a confident summary built on a search result nobody opened.

At the table
Scientist, Product, Project lead.
The gates
Every claim carries the URL of a page actually opened and read, not one seen only in a result list. Each key claim cross-checked against an independent second source or an own calculation. A single-sourced fact says so in the same sentence as the fact. Anything that could have changed since training is verified against a current source rather than memory.
The benchmark
The strongest published analysis in the domain.

The sequence

  1. State the common-sense hypothesis first and try to validate it cheaply. Escalate to a full search only if the cheap check fails. Deep research on a question one lookup answers is scored as overthought.
  2. Researcher workers gather evidence in parallel. They are read-only by design: a worker that can edit your files while gathering evidence is a worker whose evidence you cannot separate from its opinions.
  3. Findings go to reviewers whose job is to refute, not confirm, and from different angles rather than three copies of the same check.
  4. The recommendation names what is still missing, unverified, unread or only sampled. Leaving any of that unsaid counts as a failure to disclose, which is a rule about the writer rather than about the work.

The one habit worth stealing even if you never install this

Hand a finding to somebody whose job is to kill it, and drop the finding if they manage. Confirmation is the cheapest thing a model produces and the least informative.

Content and localisation

Content and localisation

Copy, translations, store metadata. The failure mode is a string that exists in one locale and silently reverts to the default in the others, discovered by a user.

At the table
Product, Designer, Editor.
The gates
Register and glossary respected per locale. Native quality over literal accuracy. Every key present in every locale in the same change, never as a follow-up. Copy touching safety routed through the project's human review ledger. And no dashes of the long or medium kind anywhere.
The benchmark
A native speaker reading it, not translation parity.

The sequence

  1. Before changing any user-facing string, every call site is found first and updated in the same change, with the count of sites touched reported back.
  2. All locale files plus the default string in code move together. The check is mechanical: the key exists in each locale, or the change is not done.
  3. Safety-adjacent copy stops at the human review gate. Not a suggestion, a stop.
  4. /brothermode:review includes the plain-language check: user-facing wording is held against a terminology map, so machinery terms do not leak into things people read.

Honest limit here

The locale completeness rule is a law the session follows, not a program that runs. If your repository has a linter that fails on a missing key, that linter is the stronger control, and BrotherMode's job is to make sure it runs after the last edit.

Ops and automation

Ops and automation

Tooling, pipelines, anything that drives a machine. The failure mode is a command that ran, reported nothing, and left the world in a state nobody checked.

At the table
Architect, Security, Project lead.
The gates
Steps are idempotent. A destructive command prints exactly what it will affect and waits for confirmation before running. Credentials are never typed and never logged. A state change is verified by reading the resulting state, not by assuming the command worked.

The sequence

  1. Ground map first, always: what is already true before anything changes.
  2. Anything irreversible is drafted, not run. The exact command and its rollback are written out for a human to execute. No session instruction lifts this.
  3. Every boundary call, network, file, subprocess, decode, gets an explicit failure path that surfaces the error. Silent failure patterns are the specific thing the code checks hunt for.
  4. Verification reads the resulting state back.

The hard floor here

Credentials are never entered. Payments are never made. Accounts are never created. Permanent deletion is never performed. Publishing is prepared and handed back. These are not defaults you can configure away. They are the boundary the whole system is built inside.

Part six

The rules you inherit

Five rules will change your working day. Everything else in the law is downstream of these.

One writer per file, claimed before the write

The claim goes into the state file before a worker launches, never after. It names the objective, the exact files, the output format, the boundaries, the termination condition, the declared effort tier, and a runnable check on the outcome. A new claim must be disjoint from every live one. Overlap means queue, never parallel.

There is deliberately no time-based expiry. A law promising a lease that expires while no code expires anything is worse than no law. A claim is released by an explicit park, complete, adopt or transfer, and a dead session's claim is adopted at close by the coordinator, never by a clock.

A claim closes only with an evidence block written inline: the exact command that ran and its last lines.

The rule that catches the coordinator

Added after the coordinator wrote claims for three workers, dispatched them, then edited four files of its own with no claim for itself. Nothing collided, which was luck. When any worker is live, the coordinator's own files get a claim too. Being the one who writes the registry is the reason to be in it, not an exemption from it.

references/fences.md, and the incident record under docs/mistakes/.

Done means a check that ran after the last edit

Evidence gathered before the final edit proves nothing about what is being delivered. The full list runs to fifteen points and a review applies every one, but four are where most work actually fails.

  • Verification runs after the final edit, not before it.
  • A calibration proves the test can fail for the intended defect. A test that cannot fail is not evidence.
  • An independent reviewer evaluates substantial work. The writer and the reviewer are never the same without a stated exception.
  • Remaining uncertainty is stated. Not implied, not omitted, stated.

references/definition-of-done.md carries all fifteen. Done is never a state a worker declares about itself; it is the result of that checklist passing.

Decisions come to you as cards, not as walls of text

A decision arrives as one card: two to four options, the recommended one first with its reason, each alternative with its tradeoff on one line. Chat text carries the evidence and the context around the card, never the option list itself. A long text list of questions is treated as a failure, not a style choice.

The last option on every key decision card is always yours: take the decision and the work under it back. That option cannot be dropped to shorten the card, and it is enforced at the storage layer, which is the strongest form this could take. A key decision offering no handback cannot be recorded at all.

Estimates are ranges with a confidence

Costs already spent are facts and print as numbers. Anything still to come prints as a range with a confidence level, never as a single number. A field the records cannot answer says not forecast yet, and that stays in, because a smoothed-over sentence carries less information than an honest gap.

The gates that stay yours, always

Never performed, under any instruction

  • Entering credentials, passwords, tokens, card or account numbers.
  • Creating accounts or signing in as you.
  • Spending money on your behalf.
  • Permanent deletion.
  • Publishing or releasing on its own. Cutting a release is a human-gated sequence, and the suite skips the release checks until a human has cut the tag.

Irreversible work is prepared and handed back: the exact command, with its rollback, for a person to run. A session instruction never waives one of these.

Where the truth lives when pages disagree

This booklet is a reading of the repository, not the repository. When something here and something there disagree, the tree wins. In order of authority:

  1. The code and its tests. python3 tools/test_all.py ending ALL GREEN is the strongest claim anyone can make about this system.
  2. capabilities.status.json. The register. Every capability state on every page is generated from it.
  3. docs/KNOWN-LIMITS.md and docs/NOT-FINALIZED.md. What is not proven, and the numbered defect register. Both are believed over the front page when they disagree with it.
  4. SKILL.md and references/. The law itself, and the files it loads when a situation applies.
  5. This booklet. Last, and happily so.
