# The problems list, 2026-08-16

Three BrotherSBE reviewers ran adversarially over this repository at the
founder's order: a principal architect on structure, a data reviewer on
the store, a security reviewer on the trust boundaries. Every finding
below is anchored to a file the reviewer read, and the sharpest ones were
EXECUTED and reproduced rather than reasoned about. All eighteen are in
docs/plan/QUEUE.json as items SBE1 to SBE18 with the same priorities.

Two were fixed the same night. Five more have closed since, each
re-verified rather than taken from a commit message: SBE1, SBE2, SBE9,
SBE10 and the install-identity half of the first-hour work. Eleven are
open. Every count on this page is recomputed when a line changes,
because a stale count sends a reader to fix something already fixed,
which happened three times in one night here.

## P0, one still wrong today

- **SBE14, redaction can be switched off by the text it redacts.** Any
  line equal to the human-block marker opens a block, an unterminated
  block runs to end of file by design, and nothing escapes the marker.
  Proven: a generated document redacted its first line and wrote the
  rest verbatim. This is the guard every other protection leans on.
- **SBE9, a purge crashes on any project whose receipt names a task.**
  CLOSED in commit `abde871`, and verified 2026-08-16 rather than taken
  from the commit message: the crash was reproduced against `abde871^`
  (`sqlite3.IntegrityError: FOREIGN KEY constraint failed`) and the same
  fixture returns cleanly at HEAD with 25 keys cleared. Root cause was
  ordering: `capability_receipts.task_id` references `tasks(task_id)`
  with no `ON DELETE` clause while `PRAGMA foreign_keys=ON` is set, and
  the parent was deleted before the child. The receipts delete now runs
  first.
- **SBE10, a purge leaves the sentinel tables behind.** CLOSED in the
  same commit, verified the same way: before the fix a purge reported 21
  cleared keys and left founder prose readable in `sentinel_knowledge`;
  after it, all four sentinel tables reach zero rows and 25 keys clear.
  The four tables carry `project_id` with no REFERENCES clause, which is
  why nothing refused.
- **WHAT IS STILL OPEN HERE, and it matters more than either defect.**
  The purge test pins the `removed` dictionary with a full equality
  assertion. That catches a table ADDED to the purge without a key, and
  it can NEVER catch a table FORGOTTEN: no key appears, the dict still
  matches, the suite stays green. That asymmetry is exactly how a
  privacy defect survived a release. No test asserts that every table
  carrying a `project_id` column is actually purged. One residual gap
  sits behind it: sentinel rows have no foreign key, so historical rows
  naming a project that no longer exists are unreachable by any purge,
  because `purge_project` refuses when the project row is absent.
- **SBE2, the gate starved because this repository's own test copied
  678 MB of agent worktrees.** FIXED tonight, verification pending in
  the current gate run: three red gates in one night, each blaming the
  install suite, each passing alone. Cost was coupled to local scratch
  volume, never to anything the suite tests.

## P1, the three that make a green result less trustworthy

  by `diff -rq ~/.claude/skills/brothermode/tools tools | grep -v __pycache__ | wc -l`.
  What remains open is NOT the skew but the DETECTOR: scripts/doctor.py
  check_install_identity (defined line 924, registered line 509) can only
  ever return SKIP, because the documented install writes no INSTALLED-FROM
  stamp (verify: `ls ~/.claude/skills/brothermode/INSTALLED-FROM`).
- **SBE11, a completed record can still be listed as active** while the
  store's own verify reports healthy, because the integrity check runs
  in one direction only and the rendered block carries no stamp.
- **SBE16, the handover zip carries whatever is in the pack with no

  redaction funnel ran, then land outside the repository past the
  commit-time secret scan.
- **SBE15, two shareable documents are written raw**, bypassing the
  withholding policy and leaning on the one guard SBE14 disables.

## P2 and P3, the structural debt

SBE3 the effects registry never refuses at runtime, only at gate time.
SBE4 three sources of truth for work items with no reconciliation, so
the idle verdict is only as true as a hand-edited file. SBE5 the store
is a nineteen thousand line module whose import cost is paid three
times on every shell command. SBE12 a receipt can certify nothing,
contradict its twin, and be dated in the future. SBE6 a registry read
by regex instead of parsed. SBE7 registry drift across the install
boundary is unchecked. SBE13 alerts have no project grain. SBE17
telemetry masks secrets but not paths. SBE8 backup litter at the root.
SBE18 is a founder decision, not an engineering fix: the committed
evidence tree carries the founder's home path in 2721 places, with no
credentials and no other-project data found; decide scrub or leave
before the repository is public.

## What the reviewers could NOT break, which matters as much

Migrations are additive and lossless across all nineteen. The
schema-ahead refusal is correct and touches nothing. Fence token
identity, pack path containment, and the consent gate all held under
attack. No credentials are in the tree. The gate's execution model,
serial with a silence budget rather than a wall clock, survived an
argument for parallelism. The store's transaction contract showed no
two-writer window. Marker injection through the packs and view
renderers is already defended, twice.

## The honest reading

The product's own discipline found these, which is the argument for the
discipline. None of the eighteen was caught by 3174 passing tests, and
that is the gap between a green gate and a true one, the same gap the
the adopter team review named from the outside.

The sharper lesson arrived on 2026-08-16, when three of these were
re-checked and found already closed. Twice the surviving defect was not
the one written down. SBE1's install skew measured zero, while its
DETECTOR could only ever return SKIP. Both purge defects were fixed,
while the test that should have caught them pins a dictionary by full
equality, which catches a table ADDED to the purge and can never catch
one FORGOTTEN. In both cases the real fault was a check that could not
reach a verdict, reading to a human as a check that passed, because the
summary line said zero failed.

Recommended order: the redaction switch first, because it is the guard
every other protection leans on and it is the last P0 still wrong. Then
the completeness test for erasure, because without it the next
forgotten table repeats SBE10 exactly. Then the debt, in queue order.
